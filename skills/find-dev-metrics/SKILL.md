# Find Developer Metrics

Автоматически обнаруживает **все кастомные метрики, созданные разработчиками** в проекте, и исключает стандартные метрики фреймворков/библиотек (Spring Boot Actuator, Kafka, Ignite, Tomcat, Hibernate и т.д.).

**Тип задачи:** автономная read-only утилита, **R1** (вне PDLC-loop'а, без обязательного evidence bundle — сам `metrics.md` является артефактом).

## Что считать «метрикой разработчика»

Метрика, которая создаётся/регистрируется явно в коде приложения через:
- `MeterRegistry.counter(name, tags...)`
- `MeterRegistry.timer(name, tags...)`
- `MeterRegistry.gauge(name, tags..., valueSupplier)`
- `MeterRegistry.distributionSummary(name, tags...)`
- `MeterRegistry.longTaskTimer(name, tags...)`
- `MeterRegistry.functionTimer(name, tags..., valueFunction)`
- `MeterRegistry.functionCounter(name, tags..., countFunction)`
- Аннотация `@Timed` (micrometer-annotations)
- Прямая регистрация через `meterRegistry.register(...)`
- Fluent-регистрация: `Counter.builder(...).register(meterRegistry)`
- Вызовы **обёрточных методов проекта** — хелперов, которые прячут `MeterRegistry` за своим API

Список обёрточных методов **не зашит**: в каждом проекте он свой. Он выводится на
Шаге 1 — сначала находятся классы, держащие `MeterRegistry`, затем их публичные
методы. Зашитый список нашёл бы метрики одного проекта и молча пропустил бы все
остальные.

## Что НЕ считать (исключения)

| Категория | Что игнорировать |
|---|---|
| **Spring Boot Actuator** | `jvm.*`, `http.*`, `system.*`, `logback.*`, `process.*`, `uptime.*`, `disk.*` |
| **Клиент Kafka** | Метрики MBean `kafka.producer.*` (если не заведены вручную в коде как кастомные) |
| **Сервер Kafka** | Метрики MBean `kafka.server.*`, `kafka.network.*` |
| **Ignite** | MBean `ignite.*` |
| **Tomcat/Jetty/Undertow** | `tomcat.*`, `jetty.*`, `undertow.*` |
| **Hibernate** | `hibernate.*` |
| **Resilience4j** | `resilience4j.*` (если заведены автостартером Spring Boot) |
| **Micrometer internals** | `micrometer.composite.*`, `micrometer.timer.*` |
| **Health/Info** | `health.*`, `info.*`, `liveness.*`, `readiness.*` |

## Алгоритм

### Шаг 0 — Preflight, без него не начинать

Скилл перезаписывает файл в корне проекта. Значит до первой записи проверяется,
что мы вообще там, где думаем, и что перезаписывать можно.

| Проверка | Как |
|---|---|
| Это Java-проект | в корне есть `pom.xml` либо `build.gradle`/`build.gradle.kts` |
| Micrometer подключён | в зависимостях или в коде встречается `io.micrometer` |
| `metrics.md` ещё не написан человеком | файла нет, либо он начинается строкой `# Developer Metrics —`, либо задан `--force` |

Третья проверка — не формальность. `metrics.md` в корне репозитория —
правдоподобное имя документа, написанного руками, и перезаписать его молча
означает потерять его без следа: файл не в `.gitignore`, но и не обязан быть
закоммичен. Заголовок `# Developer Metrics —` ставит сам скилл, поэтому файл со
своим заголовком считается своим и перезаписывается свободно.

Тексты отказа:

```
❌ /find-metrics остановлена: это не Java-проект

Текущий каталог: /work/some-service
  ❌ pom.xml / build.gradle  — не найдены

Команда запускается из корня Java/Spring Boot проекта.
Ничего не создано и не изменено.
```

```
❌ /find-metrics остановлена: Micrometer не найден

  ✅ pom.xml
  ❌ io.micrometer — нет ни в зависимостях, ни в коде

Скилл ищет метрики Micrometer. Если реестр здесь другой — метрик он не найдёт,
а пустой отчёт затрёт существующий metrics.md.
Ничего не создано и не изменено.
```

```
❌ /find-metrics остановлена: metrics.md написан не этим скиллом

  metrics.md   (изменён 2026-08-19, первая строка: «# Метрики сервиса»)

Перезапись уничтожит содержимое. Варианты:
  • посмотреть:      cat metrics.md
  • перезаписать:    /find-metrics --force
  • сохранить своё:  переименуй файл и запусти снова

Ничего не создано и не изменено.
```

### Шаг 1 — Сканирование кода

Выполнить параллельный поиск по `src/`:

| Паттерн | Что даёт |
|---|---|
| `.meterRegistry\.(counter\|timer\|gauge\|distributionSummary\|longTaskTimer\|functionTimer\|functionCounter)` | Прямая регистрация через MeterRegistry |
| `@Timed` | Аннотированные методы |
| `\.builder\(` рядом с `(Counter\|Timer\|Gauge\|DistributionSummary\|LongTaskTimer)\.` | Fluent-регистрация |
| `MeterRegistry` в полях и параметрах конструктора | **классы-обёртки** — вход в следующий проход |

#### Проход 1b — обёртки проекта

Прямой поиск по `register(` и `increment(` даёт ложные срабатывания: эти имена
носят и `ObjectMapper.registerModule`, и любой доменный счётчик. Поэтому вместо
поиска по именам методов ищутся **классы**, а уже в них — методы:

```
1. классы, где есть поле или параметр конструктора типа MeterRegistry
   → это хелперы метрик проекта (MetricsHolder, MetricsService, …)
2. в каждом таком классе — публичные методы, чьё тело вызывает
   meterRegistry.<counter|timer|gauge|…> либо <Meter>.builder(…)
   → это и есть обёрточные методы; их имена берутся из кода, а не из списка
3. вызовы этих методов по всему src/ → места регистрации метрик
```

Имена вроде `registerCounter`, `updateHistogram`, `incrementRequestsByDomain` —
результат такого прохода на одном конкретном проекте, а не входные данные.
`.register(` вне классов-обёрток метрикой **не считается**.

### Шаг 2 — Сбор имён метрик

Из найденных мест извлечь имена метрик:

1. **Стринговые литералы** — `meterRegistry.counter("my.metric.name")`
2. **Константы** — `meterRegistry.counter(MY_METRIC_CONSTANT)` → разрешить до значения
3. **Конкатенация** — `name + clusterId` → собрать паттерн и префикс

### Шаг 3 — Фильтрация исключений

Сравнить собранные имена с списком исключений (см. таблицу выше). Исключить совпадения.

### Шаг 4 — Структурный снапшот

Собрать результаты Шагов 1–3 в один JSON-объект по схеме
[`dev-metrics-scan.schema.json`](../../schemas/dev-metrics-scan.schema.json)
(`project_root`, `total_custom_metrics`, `metrics_by_type`, `metrics_files`,
`unregistered_counters`, `dynamic_metrics_summary`, `excluded_library_metrics`,
`scan_metadata`) и сохранить как `{project_root}/.dev-metrics-scan.json`.
Файл транзиентный — перезаписывается при каждом запуске и добавляется в
`.gitignore` целевого проекта инсталлятором обвязки.

**Снапшот обязан нести всё, что печатает Шаг 5.** Шаг 5 рендерит из снапшота, а
не из повторного чтения кода, — значит каждое поле отчёта должно иметь место в
записи метрики. Помимо `path`/`line`/`metric_name`/`type` это:

| Поле записи | Куда попадает в `metrics.md` | Откуда берётся |
|---|---|---|
| `description` | **Описание** | смысл из кода вокруг регистрации и использования |
| `percentiles` | **Перцентили** | аргументы `publishPercentiles` / константа проекта |
| `tags` | **Теги** | аргументы `Tags.of(...)` / `.tag(...)` |
| `jmx` | **JMX** | есть ли дублирующая MBean-регистрация |
| `prometheus` | **Prometheus** | попадает ли в экспорт `/actuator/prometheus` |
| `init_condition` | **Условия инициализации** | где и при каком условии вызывается регистрация |
| `dynamic_name_example` | **Пример полного имени** | подстановка реального суффикса |
| `section` | заголовок секции | Шаг 5, группировка по смыслу |

Поле, которое из кода не выводится, **не выдумывается**: оно опускается, и
рендер печатает `_(нет)_` для списков и `❓` для JMX/Prometheus. «Неизвестно» и
«нет» — разные ответы, и путать их в отчёте по метрикам нельзя.

Схема помечает эти поля необязательными: скан, оборвавшийся на Шаге 2, остаётся
валидным. Но валидный снапшот без них означает, что рендерить нечего, — это
видно по отчёту, а не проявляется как пустые поля в `metrics.md`.

Если в целевом проекте доступен harness (`.gigacode/scripts/validate-schemas.sh`
и Node.js), провалидировать снапшот перед рендером:

```
.gigacode/scripts/validate-schemas.sh validate dev-metrics-scan .dev-metrics-scan.json
```

Отсутствие validator'а/Node — не блокер (graceful no-op), просто пропусти проверку
и иди дальше к Шагу 5.

### Шаг 5 — Группировка и вывод

Сгруппировать **по смыслу** (не по типу), используя снапшот Шага 4 как
единственный источник данных.

Секции **выводятся из проекта**, а не берутся из готового списка: имена метрик,
пакеты, в которых они зарегистрированы, и подсистемы, которые они измеряют, у
каждого сервиса свои. Порядок:

1. сгруппировать метрики по общему префиксу имени и по пакету регистрации;
2. назвать группу тем, что она измеряет (`## Метрики входящего потока`,
   `## Метрики производительности`), а не типом Micrometer;
3. группы из одной метрики слить в `## Прочие метрики`, если их больше трёх;
4. порядок секций — от входа данных к выходу, затем производительность,
   затем состояние.

Пустых секций в файле быть не должно: секция существует, потому что в неё попала
метрика, а не потому, что она была в списке.

## Генерация output-файла

По умолчанию скилл генерирует **один файл** `metrics.md` в корне проекта (рядом с `pom.xml` / `build.gradle`).

Формат — нумерованный список метрик. **Ничего больше в файле быть не должно.**

### Структура файла

```markdown
# Developer Metrics — {project_name}

- **Всего метрик:** N
- **Counter:** N | **Timer:** N | **Gauge:** N | **DistributionSummary:** N | **LongTaskTimer:** N | **FunctionTimer:** N | **FunctionCounter:** N
- **Дата сканирования:** YYYY-MM-DD

---

## Метрики входящего потока

1. **`QuantityMessagesIn`** — Счётчик входящих сообщений от оркестратора
- **Тип:** Counter
- **Описание:** Увеличивается на единицу при каждом получении нового входящего сообщения...
- **Теги:** _(нет)_
- **JMX:** ✅ — дублируется через JMX MBean
- **Prometheus:** ✅ — попадает в экспорт по пути `/actuator/prometheus`
- **Условия инициализации:** метрика создаётся на старте приложения в @PostConstruct методе `MetricsHolder.initMetrics()`
- **Секция:** Метрики входящего потока

---
```

### Правила заполнения полей

| Поле | Что писать |
|---|---|
| **Тип** | Counter / Timer (quantile-гистограмма) / Timer (SLA-histogram) / Gauge (AtomicLong) / Gauge (AtomicInteger) / Gauge (double) / DistributionSummary / LongTaskTimer / FunctionTimer / FunctionCounter |
| **Описание** | Подробное описание: что фиксирует, в каких ситуациях увеличивается/уменьшается, как используется (Capacity Planning, SLA, мониторинг). Не короче 3 предложений. |
| **Перцентили** (Timer) | Значения из `publishPercentiles(...)` либо из константы проекта, на которую он ссылается; не нашлось — `_(нет)_` |
| **Теги** | Список тегов через запятую, или `_(нет)_` |
| **Пример полного имени** (динамические) | Имя с подставленным реальным суффиксом, например `QuantityMessagesSendedToEnricher_cluster1` |
| **JMX** | ✅ — если рядом есть дублирующая MBean-регистрация, ❌ — если её нет, ❓ — если по коду не видно |
| **Prometheus** | ✅ — если метрика попадает в экспорт `/actuator/prometheus`, ❌ — если исключена фильтром, ❓ — если экспорт в проекте не настроен явно |
| **Условия инициализации** | Где и при каком условии вызывается регистрация — с именами реальных классов и методов проекта. Четыре типовые формы: **на старте** (`@PostConstruct` в холдере метрик), **динамически на экземпляр** (регистрация в фабрике, по метрике на кластер/шард/домен), **лениво** (при первом вызове обёрточного метода), **условно** (только при определённом значении конфигурации). Форму определить по коду, а не выбрать наугад |

### Группировка по смыслу — пример, а не список

Секции определяются по Шагу 5 из самих метрик проекта. Ниже — как это выглядит
на сервисе потоковой обработки: **образец формулировок**, не набор обязательных
заголовков.

| Секция | Что вошло |
|---|---|
| `## Метрики входящего потока` | Входящие сообщения, ошибки приёма |
| `## Метрики исходящего потока` | Исходящие сообщения, ошибки отправки |
| `## Метрики работы с Ignite` | Ошибки и таймауты вызовов Ignite |
| `## Метрики обработки доменов` | Запросы без доменов, с несколькими доменами, по домену |
| `## Метрики производительности` | Таймеры обработки событий, SLA-гистограммы |
| `## Метрики состояния кластеров` | Количество фактов, активность кластеров |
| `## Метрики rule-engine` | ALLOW, REVIEW, DENY, ERROR |

Видно правило: заголовок называет **подсистему или стадию обработки**, а не тип
Micrometer и не пакет. На проекте с другой предметной областью заголовки будут
другими — и это норма, а не отклонение.

### Расположение файла

`{project_root}/metrics.md` — рядом с `pom.xml`. Перезаписывается при каждом
запуске скилла, если файл написан этим же скиллом (Шаг 0) либо задан `--force`.

**Важно:** В файле `metrics.md` должна быть ТОЛЬКО нумерованная последовательность метрик. Никаких дополнительных секций: «Архитектура», «JMX интеграция», «Типы таймеров», «Антипаттерны» и т.д.
