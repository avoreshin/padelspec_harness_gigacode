# Генерация автотестов из тест-модели релиза

Читает `docs/testcases/<release>.yaml`, созданный `/generate-test-cases`, и дописывает Cucumber-сценарии на русском Gherkin в существующие feature-файлы `orchestrator-autotest`.

**Тип задачи:** утилита тестировщика, **R1** — пишет только локальные файлы под git, откат через `git checkout`.

**Работает offline.** Ни Jira, ни TMS, ни VPN: всё нужное лежит в рабочем каталоге. Отсюда preflight без единого внешнего вызова.

---

## Аргументы

| Форма | Что берётся |
|---|---|
| `ASFMSTD-8441` | все сценарии из `docs/testcases/ASFMSTD-8441.yaml` |
| `gen-ASFMSTD-8441-01,gen-ASFMSTD-8441-05` | только перечисленные; файл выводится из префикса до `-NN` |
| `docs/testcases/ASFMSTD-8441.yaml` | явный путь |

Смешивать `id` разных релизов в одном вызове нельзя — отказ со списком найденных префиксов.

| Флаг | Что делает |
|---|---|
| — (по умолчанию) | только генерация. Ничего не запускается, стенд не трогается |
| `--verify` | плюс `dry-run`: Cucumber резолвит glue и отвечает, сматчились ли шаги. Стенд не трогается |
| `--debug` | плюс реальный прогон и цикл починки. Шлёт сообщения на общий стенд |

Флаги — лестница: `--debug` включает и `--verify`, сначала выполняется дешёвая проверка.

## Preflight

| Проверка | Как |
|---|---|
| Тест-модель есть | `docs/testcases/<release>.yaml` существует |
| Она валидна | YAML парсится, ключ `test_cases` есть, список непуст |
| Запрошенные `id` разрешаются | каждый найден в файле |
| Проект собирается Maven | `pom.xml` в корне |
| Step definitions есть | найден хотя бы один `src/main/java/**/stepdefs/*.java` с аннотацией `@Когда` или `@Тогда` |
| Каталог feature есть | `src/test/resources/features/` существует и непуст |
| Runner найден | `src/test/java/**/*.java` с `@CucumberOptions` — нужен `glue` |

Не прошло — остановиться, перечислить **всё** недостающее сразу, ничего не создавать.

### Два места, где легко ошибиться

**Step definitions лежат в `src/main/java/`**, не в `src/test/java/`. Это проект, где автотесты и есть продукт. С путём `src/test/java/` preflight падал бы на правильном проекте.

**Feature-файлы, наоборот, в `src/test/resources/features/`** — подтверждено и деревом каталогов, и `features = {"src/test/resources/features/"}` в `@CucumberOptions`. Прежняя проверка «каталог содержит `core/` либо `debug/`» удалена: **`core/` в проекте не существует**, а `debug/` — отладочные тесты вне регресса.

### Текст отказа

```
❌ /generate-autotests остановлена: это не проект с автотестами

Текущий каталог: C:\work\some-service

  ✅ pom.xml
  ❌ src/test/resources/features/            — не найден
  ❌ src/main/java/**/stepdefs/*.java        — не найдено аннотаций @Когда/@Тогда
  ❌ runner с @CucumberOptions               — не найден, glue неизвестен

Команда запускается из корня orchestrator-autotest.
Ничего не создано и не изменено.
```

### Описание проекта — читается, а при отсутствии собирается

Отдельно от preflight и **не блокирует**: скилл опирается на файлы, объясняющие, что где лежит. В проекте, где их не писали, он слеп — но это чинится, а не повод отказываться.

```bash
python3 <CORPUS> describe --project .
```

`describe` ничего не меняет и печатает, чего не хватает из четырёх:

| Файл | Что даёт |
|---|---|
| `docs/testproject.md` | карта: где feature-файлы, где step definitions, какие модули, сколько в них сценариев |
| `docs/steps/*.md` | справочник шагов по классам: аннотация, метод, пример употребления из корпуса |
| `docs/stashKeys.md` | ключи stash с частотами и модулями, где встречаются |
| `docs/tags.md` | словарь тегов: частота, в скольких модулях, где именно |

Чего-то нет — **сначала собери, потом генерируй**:

```bash
python3 <CORPUS> docs --project .
```

Файлы собираются из кода и корпуса, существующие не перезаписываются (`--force` — поверх). Скажи пользователю, что именно создано, и что это **факты, а не согласованная документация**: семантику шагов и смысл тегов дописывает человек.

Порядок здесь принципиален. Инвентарь строится из кода в любом случае (см. ниже), но `docs/steps` даёт колонку «Пример» — готовый образец строки с настоящими значениями, лучший шаблон для подстановки. Без него подстановка идёт вслепую.

## Активация прав на правку тестов

Вторым шагом, до любой записи:

```bash
bash .gigacode/scripts/test-edit-window.sh open "генерация автотестов"
```

Это **не перестраховка, а необходимость**: feature-файлы лежат под `src/test/resources/`, а `test-files-protector.sh` блокирует запись по паттерну `*/test/*` — печатает в stdout `{"decision":"deny", …}` и выходит с кодом 2.

Обоснование правомерности: генерация тестов из просмотренной человеком тест-модели **и есть** формирование acceptance criteria, а не подгонка тестов под уже написанную реализацию — то, от чего защищает хук (`.gigacode/GIGACODE.md` §2.13).

Побочное следствие разницы путей: `*StepDefinitions.java` лежат под `src/main/java/` и хуком **не защищены**. Этот скилл их и не правит — только сообщает о недостающих шагах.

## Инструменты

Помимо оркестратора прогонов (`<SETUP>` в разделе «Проверка и отладка») скилл пользуется инвентарём корпуса. Ниже он обозначен как `<CORPUS>`; путь даёт команда `/generate-autotests`.

```bash
python3 <CORPUS> describe --project .          # чего не хватает из описания
python3 <CORPUS> docs     --project .          # собрать недостающее
python3 <CORPUS> similar  "<суть>" --project . # найти сценарий-донор
```

Обе задачи детерминированные и без LLM: разбор feature-файлов и аннотаций, частоты, ранжирование по совпадению слов.

## Инвентарь шагов строится до генерации, а не после

Генерировать по статической таблице, а сверять потом — неверный порядок: таблица протухает молча. Инвентарь строится первым, и генерация идёт **только из него**.

| Источник | Роль |
|---|---|
| `src/main/java/**/stepdefs/*.java` — аннотации `@Когда`, `@Тогда` | **контракт.** По нему матчится шаг и подставляются параметры |
| `ParameterTypes.java` | словарь значений параметрических типов |
| `docs/steps/*.md` (25 файлов) | семантика: описание, привязка модуль→класс, **колонка «Пример»** |
| feature-файлы | **контракт** для тегов, стиля и **имён атрибутов** в таблицах данных |
| `docs/stashKeys.md` | ключи stash, которые кладут хуки и служебные шаги |
| `docs/tags.md` | семантика тегов; неполон, контрактом не является |
| `glue` из `@CucumberOptions` | какие пакеты в области видимости |

### Почему документация не контракт

Не из принципа, а по факту — обе документации подтверждённо разошлись с кодом:

| `docs/steps/rules.md` | Реальная аннотация |
|---|---|
| `удалить правило через отправку в kafka c id {id}` | `{string}` — типа `{id}` среди девяти `ParameterTypes` **нет** |
| `обновить в правиле "ruleName" через BACK АРМ аналитика ...` | `обновить в правиле {string} через ...` |
| `проверить (наличие\|отсутствие) ключа "key" в IGNITE Cache "cacheName"` | `{isExists}` + `{string}` |

Плейсхолдеры `"ruleName"`, `"cacheName"`, `"stashKey"` — подставленные для наглядности значения, а не синтаксис.

`docs/tags.md` неполон так же: в нём нет `@smoke` (56 вхождений в feature-файлах), нет `@rule-lib`, `@calc-lib`, `@interval-lib` и тегов очистки `@delete_subrules_kafka`, `@delete_history_fact_kafka`, `@delete_online_profiles_kafka`. Словарь тегов строится сканированием feature-файлов; `tags.md` даёт смысл.

Колонка «Пример» в `docs/steps` — самое полезное, что там есть: готовый образец строки с настоящими значениями, лучший шаблон для подстановки.

### Форматы выражений — оба

Шаги записаны в двух синтаксисах, и сопоставление обязано покрывать оба:

| Синтаксис | Пример |
|---|---|
| Regex | `@Тогда("^ждем \"(\\d+)\"\\s* (?:секунд\|секунды\|секунду)$")` |
| Cucumber Expressions | `@Когда("сохраняет id правила {string} как {string}")` |
| Смешанный с ParameterType | `@Когда("{isSwitch} GreenField для правила {string} в BACK")` |

### ParameterTypes — девять типов

| Тип | Допустимые значения |
|---|---|
| `{isSwitch}` | включить \| выключить |
| `{isExists}` | наличие \| отсутствие \| отсутствует \| присутствует |
| `{isRecord}` | есть запись \| нет записи |
| `{isAppear}` | появления \| удаления |
| `{igniteName}` | Group Operators \| Interval \| Variable \| OnlineFact \| Rule \| (пусто) |
| `{checkerType}` | Interval \| ControlAction \| (пусто) |
| `{safpCheckerType}` | Rules \| IntervalFact \| CalcProfiles |
| `{shCommand}` | start \| stop \| restart |
| `{typeSafpChecker}` | правила \| исторического факта \| онлайн факт |

Подставлять **ровно эти слова**. «Активировать» вместо «включить» — шаг не сматчится, и обнаружится это только на прогоне.

### Инвентарь атрибутов — имена полей тоже не выдумываются

Правило «не выдумывать» распространяется не только на шаги, но и на **имена параметров в таблицах данных**. Шаг может быть найден в инвентаре, а таблица под ним — содержать поле, которого в системе нет:

```gherkin
* отправить плоский JSON запрос "event" в оркестратор с параметрами
  | Канал   | MOBILE |   ← существует
  | domains | RETAIL |   ← а это откуда?
```

Шаг проверен, данные — нет, и расхождение всплывёт только на прогоне.

Инвентарь атрибутов строится тем же способом, что и инвентарь шагов — по существующим feature-файлам, которых в проекте 394 сценария. Собирается **не глобальный список, а привязанный к шагу**: имена параметров зависят от шага, и `отправить плоский JSON запрос ... с параметрами` принимает совсем не то же, что `создать онлайн-факт ... с параметрами`.

```
для каждого шага в feature-файлах:
    собрать имена из первой колонки следующей за ним таблицы
→ инвентарь: шаг → множество наблюдённых имён параметров
```

Атрибут не найден в инвентаре этого шага → **не молча писать**, а вынести в отчёт рядом с ненайденными шагами:

```
⚠️ Атрибут не встречался в существующих сценариях (gen-ASFMSTD-8441-02):
   Шаг:     отправить плоский JSON запрос "event" в оркестратор с параметрами
   Атрибут: «Признак повторной операции»
   Похожие в инвентаре этого шага: «Признак операции», «Повторная отправка»
   Проверь имя по фиче — сценарий записан как есть.
```

Инвентарь неполон по той же причине, что и инвентарь шагов: атрибут может быть валидным и просто не встречаться в существующих тестах. Поэтому формулировка — «не встречался», а не «не существует», и сценарий всё равно записывается.

### Проверка stash-переменных

Передача данных между шагами идёт через `#{имя}`. Использование переменной раньше, чем она положена в stash, — гарантированно падающий тест, и это проверяется механически.

#### Три места, где переменная может быть определена

| Источник | Пример |
|---|---|
| Блок `Предыстория:` **целевого файла** | `* сгенерировать UUID и сохранить как "id"` |
| Шаг выше в этом же сценарии | `* сгенерировать номер карты и сохранить как "CARD"` |
| `docs/stashKeys.md` | ключи, которые кладут хуки и служебные шаги |

**`Предыстория` — обязательный источник, а не дополнительный.** Она выполняется перед каждым сценарием файла, и в наблюдённой практике именно там генерируются `id`, номер карты и временные отсечки. Проверка, смотрящая только внутрь сценария, выдаст ложное предупреждение на каждую такую переменную — и человек перестанет читать предупреждения вообще.

Отсюда порядок: **сначала прочитать `Предыстория` целевого файла, потом проверять сценарий**. При дописывании в существующий файл `Предыстория` уже написана кем-то другим — читаем её как данность.

Третий источник объясняет, почему `#{ID последнего события}` валиден без явного шага сохранения.

Не нашлось нигде — предупреждение с номером шага:

```
⚠️ Stash-переменная используется до определения (gen-ASFMSTD-8441-04, шаг 3):
   #{USER_ID} — нет в Предыстории файла, нет шага сохранения выше,
                нет в docs/stashKeys.md
   Добавь шаг сохранения либо проверь имя.
```

#### Не переопределять то, что уже даёт Предыстория

Если `Предыстория` целевого файла уже кладёт `#{CARD}`, добавлять свой шаг генерации карты в сценарий не нужно: в лучшем случае это лишний шаг, в худшем — сценарий работает с одним значением, а Предыстория подготовила состояние под другое.

Правило: переменная есть в `Предыстория` → использовать её, свой шаг сохранения **не добавлять**. Нужно именно другое значение — это осознанное решение, и оно выносится в отчёт:

```
📎 Переопределение переменной Предыстории (gen-ASFMSTD-8441-02):
   #{CARD} задаётся в Предыстории файла, сценарий генерирует свою.
   Убедись, что это намеренно.
```

#### У значений в stash есть типы

Одного факта определения мало. Наблюдённое падение: `timestamp` сохранён **строкой** через шаг форматирования, а шаг вычисления времени ожидает `LocalDateTime` — `ClassCastException` на рантайме, при формально корректном сценарии.

Таблица наблюдённых типов:

| Шаг-источник | Тип значения |
|---|---|
| `сохранить временную отсечку как "X"` | `LocalDateTime` |
| `вычислить время от "X" ... в формате ... и сохранить как "Y"` | `String` (уже отформатирован) |
| `сгенерировать UUID и сохранить как "X"` | `String` |
| `сгенерировать номер карты и сохранить как "X"` | `String` |
| `сохранить значение "..." как "X"` | `String` |
| `сохраняет id правила ... как "X"` | `String` |
| `сохранить features для мерчанта ... в переменную "X"` | коллекция |

| Шаг-потребитель | Требует |
|---|---|
| `вычислить время от "X" плюс/минус N ...` | `LocalDateTime` — не отформатированную строку |

Тип источника известен и не совпадает с требуемым → предупреждение. Комбинация в таблице отсутствует → **молчать**: таблица заведомо неполна, и ложное предупреждение здесь хуже пропущенного.

```
⚠️ Несовместимый тип stash-значения (gen-ASFMSTD-8441-06, шаг 4):
   #{timestamp} сохранён как String шагом форматирования,
   а шаг «вычислить время от ...» ожидает LocalDateTime.
   Используй исходную временную отсечку (#{now}), а не отформатированную.
```

### Слепая зона

`docs/steps/*.md` описывают **только** локальные шаги из `ru.sbrf.fraud.at.orchestrator.stepdefs`. Пакеты `ru.sbrf.fraud.at.core.stepdefs`, `.web.stepdefs`, `.rest.stepdefs` подключены в `glue`, приходят транзитно из `fraud-utils:1.0.0` и не документированы нигде. Jar в `~/.m2` отсутствует, Maven не поднимается из-за корпоративного Nexus (PKIX/SSL).

Значит инвентарь **заведомо неполон**, и формулировка для ненайденного шага обязана это отражать. «Шага нет» — запрещено: она провоцирует написать дубль поверх существующей реализации.

Если jar появится локально — скилл пробует достать список шагов оттуда и говорит, что инвентарь полный.

## Ненайденный шаг

Не выдумывается: не подставляется похожий, не изобретается новый текст. Сценарий записывается как есть, шаг уходит в отчёт.

```
⚠️ Шаг не найден в инвентаре (для gen-ASFMSTD-8441-03):
   Действие из тест-модели: «Проверить отсутствие записи в топике TRIPLAN_EVENTS»

   Искали в:   KafkaStepDefinitions (аннотации), docs/steps/kafka.md
   Не покрыто: ru.sbrf.fraud.at.{core,web,rest}.stepdefs — не документированы,
               jar в ~/.m2 отсутствует; проверить на машине со сборкой

   Ближайшее:  `проверяет что в топике {string} {isRecord} с ключом {string}`
               {isRecord} = «есть запись | нет записи»
               → вероятно подходит: «нет записи». Проверь перед тем, как писать новый.

   Если не подходит — требуется новый шаг:
     Класс:      KafkaStepDefinitions
     Аннотация:  @Тогда("проверяет что в топике {string} отсутствует запись с ключом {string}")
     Сигнатура:  public void checkNoRecordInTopic(String topic, String key)
     Функционал: прочитать топик, убедиться, что записи с указанным ключом нет
                 в пределах таймаута
```

**Ближайшее совпадение показывать обязательно.** Пример выше не гипотетический: `{isRecord}` уже покрывает проверку отсутствия, и без подсказки человек написал бы дублирующий step definition поверх работающего.

## Размещение

### Дописывать в существующий файл — норма

Подтверждено git log за три месяца: `ASFMSTD-10470` дописан в `asfmstd/st/onlineFacts/`, `ASFMSTD-10354` — в `variableFact/`. **Новые feature-файлы под story не заводятся** — один файл на компонент. Создание файла остаётся редким fallback для компонента, которого ещё нет.

### Каталоги

### Выбор файла

Индекс строится перед генерацией: по каждому `.feature` — путь, `Функционал:`, теги файла, теги сценариев, названия сценариев, используемые шаги. Затем по убыванию силы признака:

1. каталог компонента содержит один `.feature` — он и есть цель (типовой случай);
2. компонентный тег совпадает с преобладающим тегом файла;
3. пересечение шагов сценария с шагами файла выше порога;
4. совпадение по строке `Функционал:`.

Ничего не совпало — новый файл, имя по компоненту в camelCase (`ruleEngine.feature`, `onlineFacts.feature`).

Выбор **объясняется по каждому сценарию**. Молчаливое размещение не годится: ошибка маршрутизации обнаружится только на прогоне регресса.

`component.confidence: none` в тест-модели → сценарий **не размещается**, а выносится в отчёт с просьбой указать компонент в YAML.

### Сначала ищется аналог в других модулях

Новый сценарий почти никогда не первый в своём роде. Нужно проверить логирование в Kafka для модуля N — почти наверняка такая проверка уже написана для модуля M, и писать её заново значит изобретать заново и чужие ошибки тоже.

**До конвертации шагов** по каждому сценарию из тест-модели ищется донор — по всему корпусу, а не только в целевом файле:

```bash
python3 <CORPUS> similar "<суть проверки>" --project . --exclude <модуль-цель> --top 5 --print
```

Запрос — суть проверки словами из тест-модели: `"проверка логирования в kafka"`, `"дедупликация событий по ключу"`. Сопоставление идёт по основам слов, поэтому «логирования» находит «Логирование»; имя сценария весит больше шагов, а `--exclude` убирает целевой модуль, чтобы в выдачу не лезли соседи по файлу.

`--print` печатает лучший сценарий целиком вместе с **Предысторией его файла** — без неё видно шаги, но не видно, что часть переменных уже определена до сценария.

Что берётся у донора и что нет:

| Берётся | Не берётся |
|---|---|
| последовательность шагов и их формулировки | ключ TMS (`@ASFMSTD-T*`) — он чужой |
| имена атрибутов в таблицах данных | значения данных: они про чужой модуль |
| приём ожидания (`ждем "5" секунд` перед проверкой топика) | компонентный тег и тег очистки — берутся по целевому каталогу |
| структура: подготовка → действие → проверка | `functionalArea` и allure-метки — у соседа по **целевому** файлу |

Донор — образец формы, а не источник данных. Скопировать его целиком, поменяв два значения, — та же ошибка, что выдумать шаг: получится сценарий про чужой модуль.

**Донор называется в отчёте.** Молча взятый образец невозможно проверить:

```
🔎 Донор для gen-ASFMSTD-8441-04 (проверка логирования в Kafka):
   asfmstd/st/ruleEngine/ruleEngine.feature:16 — «Логирование срабатывания правила в Kafka»
   модуль asfmstd/st/ruleEngine · совпало 3/3 слов запроса
   Взято: последовательность шагов, ожидание перед проверкой топика, имя поля в таблице.
```

Донор не найден — это не ошибка, а сообщение: сценарий такого рода в корпусе первый. Скажи об этом прямо, генерируй из инвентаря шагов и пометь в отчёте — такие сценарии стоит смотреть внимательнее.

### Большие файлы

`asfmstd/st/ruleEngine/ruleEngine.feature` — 5296 строк. Читать шапку (`#language`, теги файла, `Функционал:`) и хвост; вставлять в конец; существующее форматирование не трогать.

### Дедупликации против человеческих тестов нет

Связи «story → сценарий» в репозитории не существует: сценарии тегируются ключами TMS (`@ASFMSTD-T1174`), а связь TMS-кейса со story живёт в TMS в `issue_links`, куда доступа нет. Определить, написан ли уже автотест по этой story, **невозможно**.

Взамен — перед записью показать по каждой story сценарии из целевого файла, похожие по ключевым словам, вместе со счётчиком `story_tms_cases` из тест-модели. Решение принимает человек:

```
📋 Похожие сценарии уже есть в asfmstd/st/engines/engines.feature:
   ASFMSTD-T980   Выбор кластера Ignite по домену из сообщения
   ASFMSTD-T981   Дефолтный домен ANTIFRAUD при отсутствии атрибута

   Связь story↔сценарий в репозитории отсутствует — проверь на дубль сам.
```

### Перемещение

Размещение решается до записи, перемещать нечего. Единственный случай — сценарий с тегом `@gen-*` уже существует, а расчётная цель изменилась: вырезать из старого файла, вставить в новый, показать оба пути.

## Форма сценария

По живому образцу из `asfmstd/st/onlineFacts/onlineFacts.feature`.

Шапка файла (при создании нового; при дописывании **не трогается**, но читается — из неё берутся теги-образцы и блок `Предыстория:`):

```gherkin
#language:ru
@allure.label.appType:backend
@allure.label.testFramework:Cucumber
@allure.label.layer:api

Функционал: <название компонента>
```

Сценарий:

```gherkin
  #___<секция>___

  @allure.label.functionalArea:<скопировано у соседа>
  @allure.label.testStage:dev
  @gen-ASFMSTD-8441-01 @ASFMSTD-9038 @st @fact-engine @delete_online_facts_kafka
  Сценарий: gen-ASFMSTD-8441-01 FE отправляет запрос на кластер с доменом из сообщения

    * отправить плоский JSON запрос "event" в оркестратор с параметрами
      | Канал   | MOBILE |
      | domains | RETAIL |
```

### Обязательные конвенции

| Что | Правило |
|---|---|
| `#language:ru` | первая строка файла, иначе Cucumber не разберёт кириллические ключевые слова |
| Ключевые слова | кириллицей: `Функционал:`, `Сценарий:`; шаги через `*` |
| Порядок тегов | allure-метки → идентификатор → ключ story → стенд → компонент → библиотека → очистка |
| Имя сценария | начинается идентификатором, затем название |
| Разделители секций | комментарии вида `#___Duration___` |
| Комментарии к шагам | намерение шага из тест-модели переносится комментарием перед шагом |
| Таблицы параметров | выровнены по столбцам |
| Переменные между шагами | `#{имя}` (Stash) |
| JPath | `$.['Поле']`, с учётом кириллических ключей |
| `@tmsLink=` | **не выставляется** — записи в TMS нет, фальшивая ссылка сломает разбор regex-ом `@tmsLink=([A-Z]+-T?\d+)` |

### Allure-метки

Cucumber их не требует, фильтров по ним в `@CucumberOptions` нет, в `AUTOTEST_CONVENTIONS.md` они не документированы — их проставляет человек для группировки в отчётах.

Правило: метки **копируются у ближайшего соседнего сценария** в том же файле и помечаются в отчёте как скопированные. Генерировать `functionalArea` самостоятельно нельзя — неверная метка хуже отсутствующей, потому что молча портит группировку отчёта.

### Теги очистки

Документированного соответствия «шаг создания → тег очистки» в проекте **нет** — тестировщик подбирает по смыслу. Значит и скилл вывести его надёжно не может.

Скилл ведёт таблицу наблюдённых пар:

| Шаг создаёт | Предлагаемый тег |
|---|---|
| `создать правило ... kafka` / `... BACK АРМ` | `@delete_rules_kafka` / `@delete_rules_back` |
| `создать онлайн-факт ... kafka` | `@delete_online_facts_kafka` |
| `создать переменный факт ... kafka` | `@delete_variable_facts_kafka` |
| `создать субправило ... kafka` | `@delete_subrules_kafka` |
| `создать исторический факт ...` | `@delete_history_fact_kafka` |
| `создать онлайн-профиль ...` | `@delete_online_profiles_back` |
| `создать шаблон УВ E-Mail / АДАС / SMS` | `@delete_information_email_kafka` / `_adas_kafka` / `_sms_back` |

Подобранный тег помечается как **предложенный** и попадает в отчёт отдельной строкой. Если сценарий создаёт сущность, а пара не нашлась — прямое предупреждение:

```
⚠️ Тег очистки не подобран (gen-ASFMSTD-8441-05):
   сценарий создаёт сущность шагом «создать группу операторов с параметрами»,
   парного тега очистки в таблице нет. Добавь вручную — иначе сущность
   останется на стенде.
```

Молчать здесь нельзя: цена ошибки — мусор на общем стенде, который потом разгребают руками.

## Процесс

1. Preflight.
2. `bash .gigacode/scripts/test-edit-window.sh open "генерация автотестов"` — безусловно; после записи файлов закрыть окно (`... close`).
3. Разобрать аргументы → путь к тест-модели и список запрошенных `id`.
4. Прочитать YAML. Сценарии с `component.confidence: none` отложить в отчёт.
5. `describe` — если описание проекта неполно, собрать `docs` и сказать об этом пользователю.
6. Построить инвентарь шагов: аннотации → `ParameterTypes` → `docs/steps` → glue.
7. Построить индекс feature-файлов: **блок `Предыстория:`**, теги, стиль, **инвентарь атрибутов по каждому шагу**; прочитать `docs/stashKeys.md`.
8. Для каждого сценария: выбрать целевой файл, показать похожие существующие сценарии.
9. `similar` — найти донора в других модулях и взять его за образец формы.
10. Сконвертировать шаги, подставив значения по `ParameterTypes` и образцу из «Пример».
11. Сверить имена атрибутов в таблицах с инвентарём этого шага; не найдено — в отчёт.
12. Проверить stash-переменные: каждая `#{X}` определена в `Предыстория` целевого файла, шагом выше в сценарии либо перечислена в `docs/stashKeys.md`; проверить совместимость типов; не переопределять то, что даёт `Предыстория`.
13. Собрать теги в каноническом порядке; подобрать тег очистки; скопировать allure-метки у соседа.
14. Идемпотентность: тег `@gen-*` уже есть — совпало содержимое пропустить, разошлось вынести в отчёт **без перезаписи**.
15. Записать feature-файлы.
16. **Перечитать записанные файлы**, собрать из них теги `@gen-*` и сверить с тем, что собираемся напечатать (см. ниже).
17. Дописать в YAML `feature: <путь>` и `custom_fields.Автоматизирован: "Да"` в обработанные блоки.
18. Задан `--verify` или `--debug` — запустить проверку (см. «Проверка и отладка»). Без флага сюда не заходить: по умолчанию скилл не запускает ничего.

## Отчёт строится по файлам, а не по намерению

Последний шаг перед выводом: перечитать записанные feature-файлы, найти в них теги `@gen-*` и построить отчёт **из этого**, а не из списка, который скилл собирался записать.

Разница не косметическая. Сводка вида «✅ 2 файла, 9 сценариев» — это утверждение о состоянии диска, и написать его по памяти о собственном намерении значит выдать намерение за факт. Если запись частично не прошла, отчёт об этом промолчит.

Расхождение между намеченным и фактическим — не тихая правка счётчика, а отдельная строка:

```
❗ Отчёт разошёлся с файлами:
   намечено 9 сценариев, в файлах найдено 8
   отсутствует: gen-ASFMSTD-8441-07
   Проверь git diff — запись могла не пройти.
```

То же и для YAML: `feature:` проставляется только тем блокам, чьи теги реально найдены в файлах.

## Проверка и отладка

По умолчанию скилл ничего не запускает: сгенерировал, отчитался, вышел. Запуск включается флагом и идёт лестницей — каждая ступень дороже предыдущей.

### `--verify` — dry-run

`mvn test -Dcucumber.execution.dry-run=true` даёт авторитетный ответ от самого Cucumber: он резолвит glue и видит шаги из `fraud-utils`, которых нет в инвентаре. Стенд не трогается, сообщения не уходят.

Помечено как **непроверенное**: в среде, где собирались факты, Maven не поднялся из-за корпоративного Nexus, и поведение Cucumber на неизвестном шаге не подтверждено.

### `--debug` — прогон и цикл починки

**Это не read-only.** Реальный прогон шлёт сообщения на общий стенд и создаёт там сущности. Перед первым запуском — подтверждение через `AskUserQuestion`: «Прогон отправит сообщения на стенд и создаст сущности. Запускаем?» · «Да, запускать» · «Только dry-run» · «Отмена». Без явного «да» реальный прогон не запускается. `--debug --yes` пропускает вопрос.

Прогон и разбор делает `.gigacode/scripts/autotest-run.sh` — вердикт по шаблонам, а не по впечатлению от лога:

```bash
bash .gigacode/scripts/autotest-run.sh dry-run "@gen-ASFMSTD-8441-01"
bash .gigacode/scripts/autotest-run.sh run     "@gen-ASFMSTD-8441-01"
```

Скрипт печатает `VERDICT`, `SIGNATURE` и список находок; коды возврата: `0` чисто, `1` есть чинимое, `2` вне зоны, `3` инфраструктура, `4` лог не разобран.

### Зона ответственности

Граница проходит там, где сценарий перестаёт быть причиной. Скилл отвечает за то, чтобы сценарий **сматчился с реализацией, собрался и передал всё, что нужно**. Дальше — не его дело.

| `VERDICT` | Категории | Что делает цикл |
|---|---|---|
| `fix` | `step-undefined`, `step-ambiguous`, `parameter-type`, `gherkin-parse`, `stash-type`, `missing-field`, `bad-value` | чинит feature-файл и запускает снова |
| `out-of-scope` | `assertion` | **останов.** Сценарий доехал до проверки, сообщение ушло, результат не совпал с ожиданием |
| `infra` | `maven-deps`, `maven-missing`, `stand-unreachable` | **останов.** Прогона не было — чинить окружение |
| `unknown` | — | **останов.** Лог не совпал ни с одним шаблоном; отдать человеку, не додумывать |

`assertion` — это либо дефект продукта, либо неверное ожидание в тест-модели. Ни то ни другое не лечится правкой feature-файла, и подгонять сценарий под фактический результат **запрещено**: так проверка перестаёт что-либо проверять.

`missing-field` — единственная категория с оговоркой. NPE внутри шага обычно значит непереданное поле, но может оказаться и дефектом продукта. Две правки подряд не убрали её — считать `out-of-scope` и остановиться.

### Правила цикла

1. Окно правки тестов открыто на всё время цикла, закрывается один раз в конце.
2. Правятся **только** feature-файлы и, при необходимости, `Предыстория:`. Step definitions не пишутся — их отсутствие уходит в отчёт, как и без `--debug`.
3. После каждой правки — сначала `dry-run`, и только если он чист, реальный прогон.
4. **Максимум 5 итераций** на вызов. Исчерпаны — останов с журналом.
5. Две итерации подряд с одинаковой `SIGNATURE` — прогресса нет, останов. Крутиться на том же падении, меняя формулировки, запрещено.
6. Каждая итерация записывается в журнал: что упало, что поправили, что стало.
7. Останов по `out-of-scope` — **не провал скилла**. Сценарий сгенерирован верно; отчёт говорит, что проверять человеку.

### Журнал цикла в отчёте

```
🔁 Отладочный цикл: 3 итерации, останов «вне зоны»

  1. dry-run  → fix   step-undefined
     «проверяет что в топике {string} отсутствует запись»
     → заменено на `{isRecord}` = «нет записи»
  2. dry-run  → pass
     run      → fix   stash-type
     ClassCastException на #{eventDate}
     → в Предыстории значение уже LocalDateTime, лишнее форматирование убрано
  3. run      → out-of-scope  assertion
     expected: <APPROVED> but was: <DECLINED>

  ⏹️ Останов: сценарий доехал до проверки, сообщение ушло.
     Дальше — дефект продукта либо ожидание в тест-модели. Не моя зона.
     Лог: /tmp/autotest-run-XXXX.log
```

## Что этот скилл не делает

- Не обращается к Jira и TMS — работает только с файлами рабочего каталога.
- Не создаёт и не редактирует тест-модель; единственные его правки в YAML — служебные `feature:` и `Автоматизирован:`.
- Не добавляет step definitions в Java-код — только перечисляет недостающие шаги с предлагаемой сигнатурой.
- Не пишет в `debug/`, `afci/`, `afcore/`, `bigfeatures/`, `pmi/`, `prepare/`.
- Не перезаписывает сценарий, у которого тег `@gen-*` уже есть, — сообщает о расхождении.
- Не выставляет `@tmsLink=`, не выдумывает `functionalArea` и не выдумывает имена атрибутов.
- Не печатает отчёт по намерению — только по перечитанным файлам.
- Не запускает `mvn test` без `--verify` или `--debug` — выдаёт готовую команду.
- Не чинит в отладочном цикле то, что вне его зоны: провалившуюся проверку, недоступный стенд, несобравшийся Maven.
- Не подгоняет ожидание сценария под фактический результат, чтобы тест позеленел.
- Не переписывает описание проекта, написанное человеком: `docs` создаёт только отсутствующее, `--force` — по явной просьбе.
- Не копирует донора целиком: значения данных, ключ TMS и теги берутся по целевому модулю, а не у него.
