# Тест-модель релиза из состава релиза в Jira

Читает состав релиза `ASFMSTD-NNNN` (issue type `Release 2.0`), извлекает Story и порождает по ним тест-сценарии **в файл** `docs/testcases/<release>.yaml`.

**Тип задачи:** утилита тестировщика, **R1** — пишет только локальные файлы под git, откат через `git checkout`.

Конечная цель цепочки — автотесты к новым задачам релиза. Этот скилл делает первую половину: превращает состав релиза в тест-модель, которую человек читает и правит.

```
Jira: релиз (Release 2.0), состав — связанные issue
  ↓
docs/testcases/<release>.yaml   ← человек читает, правит компонент/стенд, удаляет лишнее
  ↓
/pdls:generate-autotests → сценарии дописаны в существующие .feature
```

Во внешние системы не пишется ничего. Файл под git — единственный носитель тест-модели.

## Acceptance criteria: SDD, если он есть

Тест-модель долго была сама себе критерием — её порождал этот скилл из описаний story, и проверить «а те ли это критерии» было нечем. Если в проекте есть `docs/sdd/`, критерии берутся оттуда: секция `## 4. Acceptance criteria` с блоками `AC-N` в Given-When-Then, а связь со story — строка `**Story**` в Metadata-таблице SDD.

```
docs/sdd/*.md  ──**Story**──▶  story релиза  ──ac:──▶  docs/testcases/<release>.yaml
```

Что делать:

1. Найти SDD story: `python3 .gigacode/scripts/sdd-testcoverage.py <release> --project .` покажет, у каких story SDD есть, какие `AC-*` в них и что уже покрыто. Разбирать SDD своими правилами не надо — экстрактор один на весь харнесс.
2. Порождать сценарии **по каждому `AC-*`**, а не по свободному тексту описания: Given-When-Then внутри AC уже содержит предусловие, действие и ожидаемый результат — это и есть заготовка кейса.
3. Проставить каждому кейсу `ac: AC-N` (или список, если кейс закрывает несколько). Без этого поля связь «критерий → кейс» проверить нельзя.
4. `AC-*`, на который сценарий не придумывается, **вынести в отчёт**, а не оставить молча непокрытым.

SDD в статусе `draft` критериями не считается: документ ещё меняется, и тест-модель по нему устареет молча. Скажи об этом человеку, а не строй модель по черновику.

**Нет `docs/sdd/` или нет SDD у story — работать как раньше.** Критерии извлекаются из описания story, `ac:` не проставляется, отказа нет. Требование «у каждой story approved-SDD» — это правило полного цикла `/pdls:test-workflow`, и enforce-ит его гейт `sdd-coverage-gate`, а не этот скилл. Скилл, отказывающийся работать без SDD, сломал бы все проекты, где SDD ещё не пишут.

## Три вещи, которых скилл знать не может

Это следствия устройства проекта, а не недоделки. Каждая обязана попадать в вывод, а не замалчиваться.

**Есть ли уже автотест по этой story.** В feature-файлах нет ни одного тега со ключом story: сценарии тегируются ключами TMS (`@ASFMSTD-T1174`), а связь «TMS-кейс → story» живёт в TMS в поле `issue_links`. Доступа к TMS нет, цепочка разорвана. Дедупликация против тестов, написанных человеком, **невозможна в принципе**.

Что делается взамен: `/pdls:generate-autotests` показывает похожие сценарии в целевом файле, и решение о дубле принимает человек. Счётчика уже заведённых ручных кейсов TMS в тест-модели больше нет: он жил только в таблице состава из комментария бота, а состав теперь берётся из связей issue, где этого числа нет. Придумывать его неоткуда — а показанное число, которому нечем быть подтверждённым, хуже отсутствующего.

**Стенд.** В Jira поля стенда нет; тег `@st`/`@ift`/`@psi`/`@nt` тестировщик ставит вручную. Скилл проставляет `@st` и **явно пишет, что это дефолт, а не вывод**.

**Компонент — часто.** Описания story свободные. Наблюдённый пример `ASFMSTD-9039` упоминает и `RE`, и `RuleEngine`, и формирование ответа в оркестратор — однозначного ответа там нет. Скилл предлагает до двух вариантов с цитатами-обоснованиями; выбор подтверждает человек правкой YAML.

### Шаг 0 — профиль тестового проекта

Первый запуск в проекте начинается не с Jira, а с вопроса, **что это за проект**.

Прежнее требование «`docs/steps/` непуст и `docs/tags.md` существует» — проверка одного конкретного устройства: Java, Maven, Cucumber, шаги в аннотациях. Проект на pytest, Robot Framework или без инвентаря шагов вообще она отвергает, хотя тест-модель для него строится ровно так же: тест-модель — это YAML со сценариями, она про фреймворк ничего не знает.

Поэтому:

1. `python3 <PROFILE> check` — профиль есть, схема та, `project_root` существует.
2. Профиля нет → **спроси у пользователя путь к тестовому проекту**. Не угадывай по текущему каталогу: тест-модель ведётся там, где заведён `docs/testcases/`, а автотесты могут лежать в соседнем репозитории. Затем `/pdls:test-project init <путь>` и продолжай.
3. Профиль есть → прочитай его и **дальнейшие проверки веди по нему**, а не по константам. `inventory_kind: none` — проекта без инвентаря шагов: `docs/steps/` в нём не требуется, и его отсутствие не отказ.
4. Профиль разошёлся с проектом (`check` вернул 1 с дельтой) → скажи об этом и предложи `/pdls:test-project refresh`. Тест-модель по устаревшему описанию строится, но сценарии будут ссылаться на то, чего уже нет.

`<PROFILE>` — `.gigacode/scripts/testproject-profile.py`; путь даёт команда `/pdls:generate-test-cases`.

**Почему проба — `get_issue(<release>)`.** Она за один вызов доказывает, что MCP жив, ключ разобран верно, доступ к релизу есть, и тип issue тот. Отдельная проба проекта проверяла бы меньше.

**Почему живой вызов, а не поиск конфига на диске.** Конфигурация может присутствовать и не работать: протухший токен, недоступный хост, отключённый VPN.

**Проверки `docs/harness/modules/` здесь нет.** В проекте этот каталог существует, но пуст — прежняя проверка «непуст» отвергала бы правильный проект. Контекст берётся из `docs/steps/` и `docs/tags.md`.

### Защита от затирания ручных правок

Файл существует → остановиться:

```
❌ /pdls:generate-test-cases остановлена: файл уже существует

  docs/testcases/ASFMSTD-8441.yaml   (38 сценариев, изменён 2026-08-21)

Перегенерация затрёт ручные правки — в том числе подтверждённые
компоненты и стенды. Варианты:
  • посмотреть:        cat docs/testcases/ASFMSTD-8441.yaml
  • перегенерировать:  /pdls:generate-test-cases ASFMSTD-8441 --force
  • сгенерировать автотесты:  /pdls:generate-autotests ASFMSTD-8441

Ничего не создано и не изменено.
```

`--force` перегенерирует файл целиком, но **уже выданные `id` переносит**, а не выдаёт заново — иначе перегенерация рвёт теги `@gen-*` в feature-файлах. Правила переноса — в разделе «Идентификаторы».

## Состав релиза — связи issue

Состав берётся из **связей самого релиза**: `get_issue(<release>)` возвращает `issuelinks` — issue, связанные с ним в обе стороны. Если инструмент отдаёт связи отдельно, годится `get_issue_links(<release>)`; источник один и тот же.

Комментарии релиза для состава **не читаются вовсе**. Раньше состав разбирался из Markdown-таблицы, которую публикует бот, и это был разбор чужого формата: он задаётся не нами, меняется без предупреждения, приходит несколькими версиями с разным содержимым, и правильную из них приходилось выбирать по дате. Связи — собственная структура задачи, а не текст о ней.

### Правила отбора

| # | Правило | Почему |
|---|---|---|
| 1 | Взять связанные issue типа `Story` | Только у них есть acceptance criteria |
| 2 | `Bug` отбросить | Нет критериев приёмки; проверять по ним нечего |
| 3 | Сам релиз в состав не берётся | Он вершина связи, а не участник |
| 4 | Связи `clones` / `is cloned by` **исключить** | Клон — отдельная задача другого релиза. Связь клонирования говорит о происхождении issue, а не о его принадлежности этому составу (см. «Клоны не разыменовываются») |
| 5 | Тип связи, кроме `clones`, не фильтровать | Типа «Состав релиза» (`id=11400`) в инсталляции нет: состав держится на обычных связях, и allow-list по имени типа молча терял бы story при первом же переименовании |
| 6 | Дубликаты ключей схлопнуть | Одна story может быть связана с релизом дважды разными типами |
| 7 | Ни одной Story среди связей → **стоп** | Пустой состав — это не пустая тест-модель, а неразобранный вход |

Порядок связей значения не имеет: состав — множество, а не последовательность. Номера сценариев присваиваются по порядку ключей story, чтобы файл был воспроизводим.

Текст отказа, когда состав пуст:

```
❌ /pdls:generate-test-cases остановлена: состав релиза пуст

Связей у ASFMSTD-8441: 4 — из них Story 0
  clones ASFMSTD-8102 (Release 2.0)   — исключено: связь клонирования
  relates to ASFMSTD-7515 (Bug)       — отброшено: тип issue
  relates to ASFMSTD-7516 (Bug)       — отброшено: тип issue
  is blocked by ASFMSTD-9001 (Task)   — отброшено: тип issue

Состав релиза держится на связях issue. Если story связаны с релизом
иначе — скажите, каким полем, и разбор поправят. Ничего не создано.
```

### Фильтр отменённых остаётся

Связь живёт дольше задачи: story отменяют, а связь с релизом остаётся. `issuelinks` несёт укороченный вид issue — ключ, тип, обычно статус, — но `resolution` там нет, а признак отмены в части workflow живёт только в нём. Поэтому по каждой story делается `get_issue(<key>)`, один вызов на задачу: он же нужен и за описанием, из которого выводятся критерии.

Правило — **deny-list, не allow-list**, сравнение без учёта регистра и обрамляющих пробелов:

| Поле | Отбрасываем при значении |
|---|---|
| `status.name` | начинается на `Отмен` или `Отклон`, либо `Cancelled`, `Canceled`, `Rejected` |
| `resolution.name` | `Отменено`, `Отклонено`, `Дубликат`, `Cancelled`, `Rejected`, `Duplicate`, `Won't Do`, `Won't Fix` |

Проверять оба поля: в части workflow задачу закрывают штатным статусом, а признак отмены живёт только в `resolution`.

Deny-list выбран сознательно: список рабочих статусов не фиксирован, и allow-list молча выкидывал бы живую задачу с незнакомым статусом. Deny-list ошибается в обратную сторону — лишний сценарий человек увидит в файле и удалит, тогда как пропущенная задача не видна вообще.

`statusCategory` не годится: Jira относит отменённые к той же категории `Done`, что и штатно завершённые.

Отброшенное **перечисляется в выводе** и пишется в файл блоком `skipped`. Ни одной Story не осталось — стоп, файл не писать.

### Клоны не разыменовываются

Релизы и story в этом проекте регулярно заводятся **клонированием**: у issue есть связь `clones` / `is cloned by`, а описание клона бывает короче исходного или пустым. Соблазн очевиден — сходить в исходную story и дочитать требования оттуда. Делать этого **нельзя**.

| Ситуация | Что делать |
|---|---|
| У story связь `clones <KEY>` | Читать **только саму story**. В исходную не ходить |
| Описание story пустое или ничего не даёт | Сценарии по ней не выдумывать: `skipped` с причиной `описание не содержит требований` |
| У релиза связь `clones <KEY>` | Связь исключается из состава, в исходный релиз не ходить. Состав — только собственные связи этого релиза |
| Среди связей нет ни одной Story | Стоп с текстом отказа. Не подставлять состав клонированного релиза |

Почему запрет жёсткий: клон живёт своей жизнью. Состав исходного релиза — это состав **другого** релиза, а не пустое место, которое можно занять; требования исходной story к моменту клонирования уже могли измениться, и в клоне их урезали намеренно. Подставленный чужой текст выглядит в тест-модели точно так же, как честно прочитанный, — человек не отличит и не перепроверит. Это тот же принцип, по которому не разыменовываются ссылки на Confluence: чего скилл не видел, того он не додумывает.

Связь клона при этом **не является** признаком отмены: story-клон — обычная рабочая задача, фильтр отменённых её не трогает.

### Неоднозначность разрешается человеком, а не молча

Триггеры пересекаются намеренно: `RuleEngine` встречается и у `ruleEngine/`, и у `engines/`; `domains` — и у `engines/`, и у `asfmdo/enrichers/domains/`.

Порядок:

1. один компонент набрал строго больше совпадений — берём его, `confidence: high`;
2. два лидера близко — записываем оба: основной в `component.value`, второй в `component.alternative`, `confidence: low`, и **цитату из описания** в `component.evidence`;
3. ни одного совпадения — `component.value: null`, `confidence: none`, сценарии всё равно генерируются, но помечены как требующие ручного размещения.

Выбирать молча по первому сработавшему триггеру запрещено. Цена ошибки — сценарий уедет в чужой файл и обнаружится только на регрессе.

## Разбор описания story

**Структуры в описаниях нет.** Проверено на трёх реальных story (`ASFMSTD-8353`, `ASFMSTD-9038`, `ASFMSTD-9039`): свободный текст в Jira-разметке, ссылки на Confluence, таблицы вердиктов в разметке `|...|`, выделения `{*}...{*}`. Ни bullet-list acceptance criteria, ни строк `Компонент:`, `Стенды:`, `Приоритет:` не существует — эти правила были предположением и удалены.

Практические следствия:

- acceptance criteria извлекаются из связного текста, а не по разметке;
- каждое различимое требование («если атрибут отсутствует — отправить на кластер с ANTIFRAUD») даёт минимум один сценарий;
- таблицы в описании (например матрица итоговых вердиктов по двум доменам) — источник сценариев на каждую ячейку, а не декорация;
- связь `clones` не разыменовывается: описание берётся только у самой story, даже если оно короче исходной (см. «Клоны не разыменовываются»);
- ссылки на Confluence не разыменовываются: контента за ними скилл не видит и додумывать его не должен. Если требование целиком спрятано за ссылкой — сценарий помечается `# TODO: требование в Confluence, нужна ручная доработка`.

### Правила генерации

| | |
|---|---|
| Один сценарий | одна проверяемая ситуация |
| Покрытие | все различимые требования story |
| Структура | precondition + 3–5 шагов + expected result на каждый шаг |
| Объём | 3–10 сценариев на story |
| Имя | что проверяем, без номера — номер живёт в `id` |

### Предусловия и шаги пишутся в терминах параметров шага

Тест-модель читает не только человек — из неё собирается Gherkin. Поэтому расплывчатое предусловие не просто неудобно, оно **не конвертируется**: генератор не сможет подставить параметры и вынесет шаг в отчёт как ненайденный.

| Плохо | Хорошо |
|---|---|
| «В Ignite Cache загружена карта» | «В IGNITE Cache `card-to-user-cache` загружен ключ `2200123456789012` со значением `user_id=abc`» |
| «Отправлено событие в оркестратор» | «Отправлен плоский JSON запрос `event` в оркестратор с параметрами: Канал=MOBILE, Номер карты клиента=`#{CARD}`» |
| «Правило настроено корректно» | «Создано правило `AT-R101` через отправку в kafka с условием: Операнд=Атрибут->BIN карты клиента, Оператор=Равно, Значение=Литерал->123456» |

Запрещённые формулировки: «заполнен корректно», «настроено согласно требованиям», «аналогично предыдущему сценарию», «см. выше». Каждый сценарий самодостаточен — содержимое повторяется, даже если совпадает с соседним.

Причина отличается от той, по которой самодостаточности требуют от ручных тест-кейсов. Там она нужна тестировщику, чтобы не листать документ. Здесь — генератору, чтобы собрать исполнимый шаг: имя кэша, ключ, имя топика, имя правила становятся **параметрами** шага, и если их нет в тексте, взять их неоткуда.

## Идентификаторы

```
gen-<release-key>-NN        например  gen-ASFMSTD-8441-01
```

| Правило | Почему |
|---|---|
| Префикс `gen-` обязателен | Читается как «сгенерировано, в TMS не заведено». Не матчится regex-ом `@tmsLink=([A-Z]+-T?\d+)` и не путается с ключом TMS `ASFMSTD-T1174`, на который визуально похож |
| Нумерация сквозная **по файлу**, не по story | `id` становится Cucumber-тегом и обязан быть уникален между feature-файлами |
| `NN` — два разряда с ведущим нулём | Больше 99 сценариев — три разряда |
| Не переименовывать вручную | `id` — join key между этим файлом и тегами в feature-файлах |
| При `--force` номера сохраняются | см. ниже: перегенерация переносит уже выданные `id`, а не выдаёт новые |

### `--force` не переприсваивает уже выданные id

`id` — join key: он стоит тегом `@gen-*` в feature-файлах и записан обратно в
YAML полем `feature:`. Выдать при перегенерации новую нумерацию — значит порвать
обе связи разом, причём молча: сценарий в `.feature` остаётся, но больше ни на
что не указывает.

Поэтому `--force` перечитывает существующий файл **до** генерации и переносит
номера:

| Сценарий после перегенерации | Что с `id` |
|---|---|
| Совпал по `story` + `name` со старым | берётся старый `id` |
| Совпал по `story`, `name` изменилось | берётся старый `id`, изменение показывается в выводе |
| Новый | следующий свободный номер |
| Исчез | номер **не переиспользуется** — он занят тегом в feature-файле |

Совпадение по `story` + `name` — не идеальный ключ: переформулированное название
даст «новый» сценарий. Это ошибка в безопасную сторону — лишний `id` человек
увидит в выводе, тогда как переиспользованный номер тихо привязал бы старый тег
к чужому сценарию.

Вывод обязан показать итог по всем четырём случаям:

```
♻️ --force: файл перегенерирован
  сохранено id:   9   (сценарии не изменились)
  переименовано:  1   gen-ASFMSTD-8441-04 «Домен по умолчанию» → «Дефолтный домен ANTIFRAUD»
  добавлено:      2   gen-ASFMSTD-8441-12, gen-ASFMSTD-8441-13
  исчезло:        1   gen-ASFMSTD-8441-07 — номер выведен из оборота, не переиспользуется
                      ⚠️ тег @gen-ASFMSTD-8441-07 в feature-файлах теперь ни на что не указывает
```

Единственный случай, когда связь всё же рвётся, — исчезнувший сценарий. Он и
вынесен отдельной строкой с предупреждением: удалить повисший тег может только
человек, скилл в feature-файлы не пишет.

## Формат файла

YAML, а не Markdown: файл читают оба — человек глазами и `/pdls:generate-autotests` парсером.

Схема следует `docs/MANUAL_TEST_CONVENTIONS.md` (`name`, `script.steps`, `folder`, `status`, `priority`, `custom_fields`) плюс поля, нужные генератору автотестов.

```yaml
# Тест-модель релиза ASFMSTD-8441. Сгенерирована из состава релиза в Jira.
# В TMS/Zephyr не выгружается — это единственный носитель.
#
# Проверь и поправь, затем:  /pdls:generate-autotests ASFMSTD-8441
#
# Что стоит проверить в первую очередь:
#   • component с confidence: low — скилл не смог выбрать однозначно
#   • stand — везде проставлен @st ПО УМОЛЧАНИЮ, из Jira он не выводится
# id не переименовывать: он join key с тегами в feature-файлах.

release:      ASFMSTD-8441
release_name: "Release 2026.s4.1.engine"
source:       https://jira.delta.sbrf.ru/browse/ASFMSTD-8441
composition:  {source: issue_links, linked: 5, stories: 3}
generated:    2026-08-21T14:03:00

# Связи состава, по которым сценарии не генерировались.
# Блок информационный: /pdls:generate-autotests его не читает.
skipped:
  - key: ASFMSTD-8353
    reason: cancelled
    status: "Отменено"
    summary: "Расчёт онлайн-фактов по доменам"
  - key: ASFMSTD-7515
    reason: issue_type
    status: "Bug"
    summary: "NPE в enricher при пустом user_id"

test_cases:
  - id:      gen-ASFMSTD-8441-01
    story:   ASFMSTD-9038
    component:
      value:       engines
      confidence:  low           # high | low | none
      evidence:    "«при старте приложения в логе должно фиксироваться к каким доменам подключен FE»"
      alternative: ruleEngine
    stand:   "@st"               # ДЕФОЛТ — из Jira стенд не выводится, проверь
    folder:  "/ASFMSTD-8441/"
    name:    "FE отправляет запрос на кластер Ignite с доменом из сообщения"
    objective: "Проверить выбор кластера по значению domains из сообщения"
    precondition: "В zk параметр domains содержит ANTIFRAUD, FE запущен"
    status:   "Актуальный"
    priority: "Medium"
    custom_fields:
      Вид тестирования: "Новый функционал"
      Автоматизирован:  "На автоматизации"
      Тестовый сервис:  "calc-lib"
    labels: ["@st", "@fact-engine"]
    script:
      steps:
        - description:     "Отправить событие с атрибутом domains = RETAIL"
          expected_result: "Запрос ушёл на кластер Ignite с domains = RETAIL"
        - description:     "Отправить событие без атрибута domains"
          expected_result: "Запрос ушёл на кластер с domains = ANTIFRAUD"
    # feature: проставляется командой /pdls:generate-autotests
```

`Автоматизирован` ставится в `На автоматизации` при генерации и в `Да` — командой `/pdls:generate-autotests` вместе с полем `feature`.

Файл кладётся в `docs/testcases/`. Каталог свободен, `docs/` не заигнорен.

**Коммит делает человек, а не скилл.** Вне git тест-модель не существует нигде, поэтому её надо закоммитить — но это отдельное решение человека, который сначала правит компоненты и стенды. Скилл останавливается на записанном файле и говорит, что дальше; `git add`, `git commit`, `git checkout -b`, `git push` он не выполняет ни при каком исходе.

## MCP-инструменты

Только чтение Jira. Инструменты TMS/Zephyr не используются.

| Инструмент | Назначение |
|---|---|
| `get_issue(key)` | preflight-проба; релиз со связями (`issuelinks`), story, статусы, `resolution` |
| `get_issue_links(key)` | то же множество связей, если инструмент отдаёт их отдельно от issue |
| `search_issues(jql)` | список релизов: `project = ASFMSTD AND issuetype = "Release 2.0"` |

`get_comments()` больше не нужен: комментарии релиза не читаются вовсе. `get_link_types()` не нужен тоже — тип связи не фильтруется, кроме исключения `clones`. Ходить по связям `clones` / `is cloned by` за описанием или составом **запрещено** — см. «Клоны не разыменовываются».

## Выгрузка в TMS — через XML-импорт, третьим шагом

MCP к TMS в инсталляции нет, и это ограничение подтверждено не только у нас: соседняя команда, работающая с тем же Zephyr Scale, зафиксировала его в своих конвенциях и обошла **файловым импортом**. Zephyr Scale принимает XML массовой загрузкой через интерфейс — ни API, ни токенов, ни MCP.

Поэтому выгрузка не «когда-нибудь», а **третий шаг конвейера**, и он замыкает цепочку. Команда — `/pdls:export-testcases-xml <release>`, инструмент — `.gigacode/scripts/export-testcases-xml.py`:

```
/pdls:generate-test-cases  →  YAML       (тест-модель)
/pdls:generate-autotests   →  .feature   (+ YAML: feature:, Автоматизирован: Да)
/pdls:export-testcases-xml →  XML        (человек загружает в Zephyr)
```

Порядок именно такой: XML собирается **после** генерации автотестов, чтобы в Zephyr уезжали кейсы с уже проставленным признаком автоматизации и ссылкой на feature-файл, а не «на автоматизации».

Схема YAML под это готова с самого начала — она следует `MANUAL_TEST_CONVENTIONS.md`, и её поля ложатся на XML один к одному:

| YAML | XML |
|---|---|
| `name` | `<name>` |
| `objective` | `<objective>` |
| `precondition` | `<precondition>` |
| `priority`, `status` | `<priority>`, `<status>` |
| `folder` | `<folder>` |
| `custom_fields.*` | `<customField name="...">` |
| `script.steps[]` | `<testScript type="steps">` |

`id` сценария уходит в XML **отдельным label**: после импорта Zephyr выдаст свои ключи `ASFMSTD-T####`, и без этой метки их нечем сопоставить с тегами `@gen-*`. Обратная привязка — отдельным проходом: найти сценарии по `@gen-*` и дописать рядом `@<TMS-key>` и `@tmsLink=`. Поле `id` при этом не исчезает: теги уже проставлены по нему, и переклейка означала бы переписать все feature-файлы.

## Что этот скилл не делает

- Не пишет ничего в Jira и TMS — только читает.
- Не генерирует Cucumber feature-файлы — это `autotest-generator`.
- Не перезаписывает существующий файл без `--force`.
- Не разыменовывает ссылки на Confluence и не додумывает то, что за ними.
- **Не делает коммит и вообще не трогает git.** Записал файл — остановился.
- Не ходит в исходную story или исходный релиз по связи `clones` — ни за требованиями, ни за составом.
- Не решает за человека спорный компонент и не выдаёт дефолтный стенд за вывод.
