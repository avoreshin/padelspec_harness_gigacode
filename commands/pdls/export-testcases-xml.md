Собери XML для импорта в Zephyr: {{args}} (ключ релиза `ASFMSTD-NNNN` либо путь к YAML; флаги `--out <файл>`, `--force` — перезаписать существующий XML).

**Тип задачи:** утилита тестировщика, **R1** — пишет один локальный файл. Вне PDLC-loop'а, phase-gate transition не выполняется.

## Место в конвейере

```
/pdls:generate-test-cases   →  docs/testcases/<release>.yaml   (тест-модель)
/pdls:generate-autotests    →  *.feature  + YAML: feature:, Автоматизирован: Да
/pdls:review-autotests      →  вердикт: сценарии проверяют то, что просила тест-модель
/pdls:export-testcases-xml  →  docs/testcases/<release>.xml    ← человек грузит в Zephyr
```

Порядок именно такой. XML собирается после генерации, чтобы в Zephyr уезжали кейсы с уже проставленным признаком автоматизации, а не «на автоматизации», и после ревью — потому что кейс, чей автотест проверяет не то, уедет в TMS как покрытый автоматизацией, и дальше на него будут полагаться.

**Почему файлом, а не API.** MCP к TMS в инсталляции нет, API закрыт. Zephyr Scale принимает массовую загрузку файлом через интерфейс — ни токенов, ни сети со стороны команды не требуется.

## Инструмент

```bash
python3 ${extensionPath}/scripts/export-testcases-xml.py <release-key> [--out FILE] [--force]
```

Сам XML руками не собирай и текстом не правь: экранирование, порядок элементов и нумерация шагов — задача скрипта. Твоя работа — запустить его, разобрать вывод и объяснить человеку, что делать дальше.

Коды возврата: `0` — записан · `1` — тест-модель неполна либо XML уже есть (нужен `--force`) · `2` — ошибка вызова или YAML не разобран.

## Проверка перед записью

Скрипт останавливается и **ничего не пишет**, если в тест-модели: нет `test_cases`; у сценария нет `id` (после импорта его не сопоставить с тегом `@gen-*`); `id` повторяется; нет `name`; нет `script.steps`; шаг без `description` или без `expected_result`.

Перечисляются **все** проблемы сразу. Не чини их вслепую сам: неполный кейс, уехавший в TMS, становится там мусором, который потом чистят руками. Покажи список человеку и предложи поправить YAML.

## Что уходит в XML

| YAML | XML |
|---|---|
| `name`, `objective`, `precondition` | `<name>`, `<objective>`, `<precondition>` |
| `status`, `priority`, `folder` | `<status>`, `<priority>`, `<folder>` |
| `id` + `labels[]` | `<labels><label>` — **`id` первым** |
| `custom_fields.*` | `<customField name="...">` |
| `script.steps[]` | `<testScript type="STEPS">` с `<step index="N">` |

**`id` уходит отдельным label намеренно.** После импорта Zephyr выдаёт свои ключи `ASFMSTD-T####`, и без метки `gen-<release>-NN` их нечем сопоставить с тегами `@gen-*` в feature-файлах: связи story↔сценарий в репозитории нет. Обратная привязка ключей — отдельный проход, и он опирается на этот label.

Не уходят: `story`, `story_tms_cases`, `component`, `stand`, `feature`, блок `skipped` — в маппинге импорта таких полей нет. `feature` при этом остаётся в YAML: признак автоматизации едет через `custom_fields.Автоматизирован`.

`folder` по умолчанию — `/<release>/`, `status` — `Актуальный`, `priority` — `Medium`. Проставленные по умолчанию значения скрипт считает и печатает; передай эту строку человеку, а не проглатывай.

## Повторный запуск

Существующий XML не перезаписывается без `--force`: повторная загрузка того же файла заводит в Zephyr **дубли кейсов**. Уже импортированные кейсы скрипт не знает и отследить не может — это ответственность человека.

## Next step

Человек загружает файл в Zephyr и проставляет выданные ключи рядом с тегами `@gen-*`. **Коммит команда не делает** — ни `git add`, ни `git commit`, ни `git push`: XML остаётся в рабочем дереве, решение о коммите за человеком.
