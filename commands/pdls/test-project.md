Работа с профилем тестового проекта: {{args}} (`init [<путь>]` · `check` · `refresh` — по умолчанию `check`; флаги `--apply` для refresh, `--force` для init).

**Тип задачи:** утилита тестировщика, **R1** — пишет только локальные файлы под git. Вне PDLC-loop'а, phase-gate transition не выполняется. Во внешние системы не ходит.

```
<PROFILE>  ${extensionPath}/scripts/testproject-profile.py    профиль: init · check · refresh
<CORPUS>   ${extensionPath}/scripts/autotest-corpus.py        описание: describe · docs · diff
```

## Зачем

Команды тестировщика написаны по одному проекту: Java, Maven, Cucumber с русской локалью, шаги в аннотациях, feature-файлы в `src/test/resources/features/`. Всё это было зашито в них константами — и на проекте с другим устройством они отвергали правильный каталог либо генерировали по несуществующим правилам.

Профиль — единственное место, где живут ответы на «где тесты», «чем запускается», «есть ли инвентарь шагов и как он устроен». Остальные команды читают его, а не угадывают.

Второе: проект живёт. Появляются шаги, теги, модули; описание в `docs/` устаревает **молча**, и генерация начинает опираться на то, чего уже нет, а нового не знает. `refresh` показывает расхождение.

## `init` — первый запуск

```
/pdls:test-project init                    # тестовый проект — текущий каталог
/pdls:test-project init ../orchestrator-autotest
```

1. Спроси у пользователя путь к тестовому проекту, **если он не задан аргументом** и текущий каталог на проект автотестов не похож (нет ни `.feature`, ни каталога тестов). Не угадывай молча.
2. `python3 <PROFILE> detect --project <путь>` — что видно в каталоге. Ничего не пишет.
3. Покажи, что определилось, и **спроси подтверждения**. Фреймворк не распознан (`framework: other`) — это не отказ: профиль пишется с пустыми полями, их заполняет человек.
4. `python3 <PROFILE> init --project <путь>` — запись `docs/test-project-profile.md`.
5. `python3 <CORPUS> describe --project <путь>` → чего не хватает из описания; отсутствующее собрать `<CORPUS> docs`.
6. Скажи, что в профиле заполняет человек: как проверяется результат (топик Kafka, кэш Ignite, база, REST, лог), стенды, чего делать нельзя, особенности. **Раздел «Как проверяется результат» — тот самый, из-за которого сценарий проверяет лог вместо топика.**

Профиль уже есть — `init` его не трогает и говорит об этом. Перезаписать: `init --force`.

## `check` — по умолчанию

```
/pdls:test-project
```

`python3 <PROFILE> check` — профиль есть, схема та, каталог из `project_root` существует, счётчики совпадают с фактическими. Коды: `0` — актуален, `1` — нет профиля либо разошёлся, `2` — ошибка.

Профиля нет → предложи `init`, не создавай молча.

## `refresh` — актуализация

```
/pdls:test-project refresh            # показать дельту, ничего не писать
/pdls:test-project refresh --apply    # применить
```

1. `python3 <PROFILE> refresh` — дельта фактов: фреймворк, раскладка, число feature-файлов, сценариев, тегов, шагов.
2. `python3 <CORPUS> diff` — что появилось в коде, а в описании ещё нет: новые шаги (аннотации), новые теги, новые ключи stash; и обратное — шаги, которые в описании есть, а в коде уже нет.
3. Покажи обе дельты и **спроси подтверждения** до записи.
4. `--apply` → `python3 <PROFILE> refresh --apply` и `python3 <CORPUS> docs --update`.

**`docs --update` не трогает файлы, правленные руками.** Признак — сгенерированный заголовок в начале файла: как только его сняли или файл дописали, он считается человеческим. Такие перечисляются в отчёте, а что в них устарело — видно в `diff`. Переписать поверх может только `docs --force`, и это делается по явной просьбе, а не «заодно».

## Что человек дописывает сам

Автоматика видит раскладку каталогов и аннотации. Она не видит договорённостей команды: через какие каналы тест видит эффект, какие есть стенды и чем отличаются, какие каталоги вне регресса, как чистятся общие сущности. Эти разделы профиля пишет человек, и `refresh` их сохраняет.
