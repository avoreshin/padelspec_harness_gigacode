```
<READY>    ${extensionPath}/scripts/release-readiness.py     статус SDD по каждой story
<PROFILE>  ${extensionPath}/scripts/testproject-profile.py   где искать SDD
```

## Зачем отдельная команда

Циклы идут в разных репозиториях: автотесты в `orchestrator-autotest`, разработка — в своём. Разными людьми и в разных сессиях. Поэтому «запустить их одной командой» невозможно физически: обвязка не может вести чужой цикл в чужом репозитории.

Что возможно — **сверить состояние**, и артефакт для этого у циклов общий. Статус SDD и есть протокол между ними:

| Статус | Что означает | Что разрешает |
|---|---|---|
| нет SDD | критерии не зафиксированы | ничего |
| `draft` | критерии ещё меняются | ничего: тест-модель по черновику устареет молча |
| `approved` | критерии зафиксированы | `model` → `autotests` → `review` |
| `implemented` | dev-цикл по story закрыт | **прогон** |

Отсюда и форма связи: фазы до прогона выводятся из критериев, а не из кода, и идут параллельно разработке. Барьер один, и стоит он перед `run`.

## Evidence bundle разработки здесь не читается

Он лежит по одному пути на репозиторий (`.gigacode/evidence-bundle.json`), перезаписывается каждой следующей задачей и обычно не под git — чужой и недостоверный источник. `implemented` же ставится человеком ровно после фазы evidence dev-цикла и живёт в самом SDD, то есть в файле, который тестировщик и так читает.

## Где берётся каталог SDD

По порядку: аргумент `--sdd-dir` → профиль тестового проекта → `docs/sdd` рядом с тест-моделью.

Средняя ступень — рабочая. В профиле (`docs/test-project-profile.md`) для этого есть две строки:

```
dev_repo: ../orchestrator          # корень репозитория разработки
sdd_dir:                           # пусто = <dev_repo>/docs/sdd
```

Заполняются человеком, `refresh` их сохраняет. Не заполнены — SDD ищутся рядом с тест-моделью, и в раздельном раскладе каждая story окажется без критериев. Отчёт всегда печатает каталог, в котором искал: «story без SDD» и «SDD искали не там» — разные диагнозы.

## Процесс

1. `python3 <READY> <release> --project .` — статус по каждой story состава.
2. Разобрать вывод и **назвать причину по каждой незакрытой story**: критериев нет вовсе (работа человека) либо критерии есть, а dev-цикл не закрыт (ждём его фазу evidence).
3. `READY` — сказать отдельно, что обвязка не наблюдает **какая сборка стоит на стенде**, и спросить подтверждение у человека (`AskUserQuestion`) перед предложением прогона.
4. Подтверждение и его отсутствие одинаково идут в свод по релизу — как факт, а не как допущение.

Команда ничего не чинит и никуда не ходит: она читает SDD и тест-модель.

## Next step

`READY` → барьер снят, `/pdls:test-run <release>` (подтвердив сборку на стенде).
`NOT READY` → фазы до прогона не заблокированы: тест-модель и сценарии строятся по критериям и ждать разработку не обязаны. Гейт `sdd-coverage-gate` держит только переход в `run`.
