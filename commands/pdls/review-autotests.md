Проведи ревью сгенерированных автотестов: {{args}} (ключ релиза `ASFMSTD-NNNN`, список `id` через запятую либо путь к YAML; флаг `--json` — машинный вывод).

**Тип задачи:** утилита тестировщика, **R1** — ничего не пишет вообще. Вне PDLC-loop'а, phase-gate transition не выполняется.

**Mandate (§2.11, как у Review Agent):** Read / Grep / Bash-чтение. **Правки в feature-файлы и в тест-модель не вносить** — ни «заодно», ни «очевидные». Ревьюер, который сам чинит найденное, перестаёт быть второй парой глаз: он проверяет уже свою работу.

Выполни skill `autotest-review`. Полная спецификация — в `${extensionPath}/skills/autotest-review/SKILL.md`.

```
<REVIEW>  ${extensionPath}/scripts/autotest-review.py    механическая сверка
```

## Зачем отдельный шаг

В PDLC-loop'е между `/pdls:implement` и `/pdls:evidence` стоит `/pdls:review`: сгенерированный код сверяется с SDD и acceptance criteria, потому что «тесты зелёные» и «сделано то, что просили» — разные утверждения. У автотестов ровно та же дыра, и тест-модель `docs/testcases/<release>.yaml` — это и есть их acceptance criteria.

Проверки генератора **структурные**: шаг существует в инвентаре, имя атрибута встречалось, stash-переменная определена, тип совпал. Все они проходят на сценарии, который проверяет не то:

```
тест-модель:  «В топике AUDIT_LOG есть запись со статусом DECLINED»
сценарий:     * проверить наличие строки "DECLINED" в логе приложения на машине
```

Шаг найден, синтаксис верен, `dry-run` зелёный, а проверка ушла из Kafka в лог на машине. Ловится это только сверкой намерения с реализацией.

## Что сверяется механически

| Находка | Уровень | Что значит |
|---|---|---|
| `channel-drift` | Blocker | ожидание в одном канале (топик Kafka), проверка — в другом (лог, кэш, БД) |
| `polarity-drift` | Blocker | «отсутствует» превратилось в «присутствует» |
| `no-assertion` | Blocker | в тест-модели есть `expected_result`, в сценарии нет ни одного шага-проверки |
| `scenario-missing` | Blocker | в YAML проставлен `feature:`, а тега `@gen-*` в файлах нет |
| `object-missing` | Major | топик, кэш или домен из тест-модели в сценарии не встречается |
| `step-uncovered` | Major | шаг тест-модели не нашёл соответствия |
| `precondition-missing` | Major | предусловие не отражено ни Предысторией, ни шагами |
| `assertion-extra` | Minor | сценарий проверяет то, чего нет в тест-модели |
| `stand-mismatch` | Minor | стенд из тест-модели не совпал с тегами |

Verdict по худшей находке: `BLOCK` · `REQUEST CHANGES` · `APPROVE`. Коды возврата скрипта: `0` — APPROVE, `1` — есть находки, `2` — ошибка вызова.

## Чего механика не видит

Скрипт сравнивает слова, а не смысл. Он не отличит проверку правильного поля от проверки соседнего, не поймёт, что ожидание в тест-модели само по себе неверно, и не увидит, что сценарий проверяет следствие вместо причины. Это разбирает агент — глазами, по каждому сценарию с находками и по каждому, где сверка прошла подозрительно гладко.

**Комментарии в сценарии в сверке не участвуют.** Генератор переносит намерение шага из тест-модели комментарием перед шагом — сверка вместе с ними всегда была бы зелёной: сравнивали бы тест-модель с её же копией.
