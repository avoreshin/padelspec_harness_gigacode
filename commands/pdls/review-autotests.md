Проведи ревью сгенерированных автотестов: {{args}} (ключ релиза `ASFMSTD-NNNN`, список `id` через запятую либо путь к YAML; флаги `--json` — машинный вывод, `--fix` — починить то, что чинится механически).

**Тип задачи:** утилита тестировщика, **R1** — ничего не пишет вообще. Вне PDLC-loop'а, phase-gate transition не выполняется.

**Mandate (§2.11, как у Review Agent):** сверка — Read / Grep / Bash-чтение, **правок не вносит**. Ревьюер, который правит по ходу сверки, перестаёт быть второй парой глаз: он проверяет уже свою работу. Поэтому починка — отдельный шаг, отдельный скрипт и явный флаг `--fix`; сам `autotest-review.py` не пишет ничего никогда.

Выполни skill `autotest-review`. Полная спецификация — в `${extensionPath}/skills/autotest-review/SKILL.md`.

```
<REVIEW>  ${extensionPath}/scripts/autotest-review.py    механическая сверка (не пишет ничего)
<FIX>     ${extensionPath}/scripts/autotest-fix.py       починка находок (пишет только с --apply)
```

## Зачем отдельный шаг

В PDLC-loop'е между `/pdls:implement` и `/pdls:evidence` стоит `/pdls:review`: сгенерированный код сверяется с SDD и acceptance criteria, потому что «тесты зелёные» и «сделано то, что просили» — разные утверждения. У автотестов ровно та же дыра, и тест-модель `docs/testcases/<release>.yaml` — это и есть их acceptance criteria.

Проверки генератора **структурные**: шаг существует в инвентаре, имя атрибута встречалось, stash-переменная определена, тип совпал. Все они проходят на сценарии, который проверяет не то:

```
тест-модель:  «В топике AUDIT_LOG есть запись со статусом DECLINED»
сценарий:     * проверить наличие строки "DECLINED" в логе приложения на машине
```

Шаг найден, синтаксис верен, `dry-run` зелёный, а проверка ушла из Kafka в лог на машине. Ловится это только сверкой намерения с реализацией.

## Что сверяется механически

| Находка | Уровень | Что значит |
|---|---|---|
| `channel-drift` | Blocker | ожидание в одном канале (топик Kafka), проверка — в другом (лог, кэш, БД) |
| `polarity-drift` | Blocker | «отсутствует» превратилось в «присутствует» |
| `no-assertion` | Blocker | в тест-модели есть `expected_result`, в сценарии нет ни одного шага-проверки |
| `scenario-missing` | Blocker | в YAML проставлен `feature:`, а тега `@gen-*` в файлах нет |
| `object-missing` | Major | топик, кэш или домен из тест-модели в сценарии не встречается |
| `step-uncovered` | Major | шаг тест-модели не нашёл соответствия |
| `precondition-missing` | Major | предусловие не отражено ни Предысторией, ни шагами |
| `assertion-extra` | Minor | сценарий проверяет то, чего нет в тест-модели |
| `stand-mismatch` | Minor | стенд из тест-модели не совпал с тегами |

Verdict по худшей находке: `BLOCK` · `REQUEST CHANGES` · `APPROVE`. Коды возврата скрипта: `0` — APPROVE, `1` — есть находки, `2` — ошибка вызова.

## Гейт

`autotest-review-gate.sh` (PreToolUse на Bash) **пересчитывает** ревью и на вердикте `BLOCK` отдаёт `exit 2` в двух точках:

| Когда | Что блокируется |
|---|---|
| конец генерации — `test-edit-window.sh close` | нельзя объявить генерацию законченной: автотест, проверяющий не то, зеленеет и создаёт видимость покрытия |
| выгрузка — `export-testcases-xml.py` | нельзя увезти в TMS кейс, чей автотест проверяет не то |

Вердикт не читается из файла намеренно: записанный протухает молча после любой перегенерации. Окно фазы Test PDLC-loop'а гейт не трогает — различает по причине, с которой окно открывали.

`REQUEST CHANGES` выгрузку не блокирует — печатает находки в stderr и пропускает. Blocker означает «сценарий проверяет не то», major — «проверяется, возможно, не всё», и его закрытие часто требует шага, которого в проекте ещё нет. Гейт, блокирующий и на major, был бы неснимаемым — и его сняли бы целиком.

Снять осознанно: `/pdls:harness hooks disable autotest-review-gate` (**R2**, причину — в commit message или evidence bundle).

## `--fix` — что чинится механически

```
/pdls:review-autotests ASFMSTD-8441 --fix
```

Цикл: ревью → `<FIX> --apply` → ревью, максимум **3 итерации**, останов при отсутствии прогресса (тот же набор находок дважды подряд).

| Находка | Чинится | Чем |
|---|---|---|
| `polarity-drift` | да | парное значение `ParameterType` в том же шаге |
| `stand-mismatch` | да | тег стенда из тест-модели |
| `object-missing` | да, если в шаге-проверке ровно один литерал | подстановка имени объекта |
| `channel-drift` | да, если в инвентаре есть шаг нужного канала и все его параметры выводятся | замена шага |
| `no-assertion` | да, на тех же условиях | дописывание шага-проверки |
| `step-uncovered`, `assertion-extra`, `precondition-missing`, `scenario-missing` | нет | это про содержание сценария, а не про его форму |

**Граница та же, что у генератора: шаг не изобретается.** Починка либо подставляет значение из `ParameterTypes`, либо ставит шаг, уже существующий в инвентаре step definitions. Параметры берутся из тест-модели и из переменных, определённых в Предыстории или выше по сценарию; недостающий параметр — причина отказаться от починки, а не повод придумать значение. Кандидатов больше одного — выбирает человек.

Без `--apply` скрипт печатает план и не пишет ничего. Три корзины в отчёте: **чинится**, **снимется вместе с правкой выше** (находка про ту же строку) и **остаётся человеку**.

## Чего механика не видит

Скрипт сравнивает слова, а не смысл. Он не отличит проверку правильного поля от проверки соседнего, не поймёт, что ожидание в тест-модели само по себе неверно, и не увидит, что сценарий проверяет следствие вместо причины. Это разбирает агент — глазами, по каждому сценарию с находками и по каждому, где сверка прошла подозрительно гладко.

**Комментарии в сценарии в сверке не участвуют.** Генератор переносит намерение шага из тест-модели комментарием перед шагом — сверка вместе с ними всегда была бы зелёной: сравнивали бы тест-модель с её же копией.

## Output (в чат)

```
## Autotest Review — ASFMSTD-8441
Verdict: BLOCK · сверено 9 · не автоматизировано 2 · потеряно 0

### Blockers (2)
- gen-ASFMSTD-8441-02 · channel-drift
  ожидание: «В топике AUDIT_LOG есть запись со статусом DECLINED»
  в сценарии: * проверить наличие строки "DECLINED" в логе приложения на машине
  → проверка ушла из Kafka в лог на машине; шаг для топика есть:
    `проверяет что в топике {string} {isRecord} с ключом {string}`

### Major (1) · ### Minor (3)
...

Правки не внесены — это ревью. Починить механическое: /pdls:review-autotests <release> --fix
```

С `--fix` добавляется журнал цикла:

```
🔧 Починка: итерация 1 — применено 5, снялось следствиями 4, осталось 2
   channel-drift gen-…-02: лог на машине → `проверяет что в топике {string} {isRecord} с ключом {string}`
   Verdict: BLOCK → REQUEST CHANGES
⏹️ Останов: оставшиеся находки механически не чинятся.
```

## Next step

Verdict `APPROVE` → `/pdls:export-testcases-xml <release>`.
Verdict `REQUEST CHANGES` → выгрузка разрешена, но находки стоит разобрать.
Verdict `BLOCK` → выгрузка заблокирована гейтом; `--fix` чинит механическое, остальное — за человеком. **Коммит команда не делает.**
