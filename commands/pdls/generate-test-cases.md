Построй тест-модель релиза: {{args}} (ключ релиза `ASFMSTD-NNNN` типа `Release 2.0` либо ссылка; флаг `--force` — перезаписать существующий файл, сохранив уже выданные `id`).

**Тип задачи:** утилита тестировщика, **R1** — пишет только локальные файлы под git. Вне PDLC-loop'а, phase-gate transition не выполняется.

Выполни skill `tc-from-release`. Полная спецификация — в `${extensionPath}/skills/tc-from-release/SKILL.md`.

## Куда попадает результат

В файл `docs/testcases/<release>.yaml`, и больше никуда. В TMS/Zephyr не выгружается, ключей `ASFMSTD-T####` не выпускается — идентификатор локальный, вида `gen-ASFMSTD-8441-01`, и он же становится Cucumber-тегом.

```
Jira: релиз + таблица состава в комментарии → docs/testcases/<release>.yaml → человек правит → /pdls:generate-autotests
```

## Preflight — обязателен

| Проверка | Как |
|---|---|
| Jira MCP настроен и живой | живой вызов `get_issue(<release-key>)` |
| Это релиз | issue type в ответе — `Release 2.0` |
| Контекст проекта на месте | `docs/steps/` непуст **и** `docs/tags.md` существует |
| Файл ещё не создан | `docs/testcases/<release-key>.yaml` отсутствует, либо задан `--force` |

Проверка не прошла — **останови работу**, перечисли всё недостающее сразу, не создавай ничего. Тексты отказов — в skill'е.

Проверки TMS здесь нет намеренно: команда туда не пишет. Проверки `docs/harness/modules/` тоже нет — в проекте этот каталог существует, но **пуст**, и прежнее требование «непуст» отвергало бы правильный проект.

## Процесс

1. Preflight.
2. Прочитать комментарии релиза. Состав релиза — **Markdown-таблица в комментарии бота `JIRA_TECHUSER_S`**; link type `11400` не существует, `fixVersion` не используется, description релиза пуст.
3. Взять **последний по времени** комментарий с таблицей. Их бывает несколько с разным составом — отменённые story заменяют новыми. Сортировать по дате создания, а не по названию стадии.
4. Разобрать таблицу по заголовкам колонок («Тип Issue», «Номер»), не по позициям.

| Строка | Действие |
|---|---|
| тип `Release` с ключом самого релиза | отбросить — это итоговая сумма |
| тип `Bug` | отбросить — нет acceptance criteria |
| тип `Story` | взять в работу |
| `{{X/Y ...}}` | прочитать **только первую пару**: `X` — ручные кейсы TMS по НФ, `Y` — регрессионные. Смысл остальных четырёх пар нигде не документирован |

5. По каждой Story — `get_issue()`, отбросить отменённые: `status.name` на `Отмен`/`Отклон` либо `Cancelled`/`Canceled`/`Rejected`; либо `resolution.name` ∈ `Отменено`, `Отклонено`, `Дубликат`, `Cancelled`, `Rejected`, `Duplicate`, `Won't Do`, `Won't Fix`. Статуса в таблице нет, поэтому вызов на каждую строку обязателен.
5a. **По связи `clones` не ходить.** Релизы и story заводятся клонированием; описание клона бывает короче исходного. Читается только сама story и только комментарии самого релиза. Описание пустое — story уходит в `skipped` с причиной, а не дочитывается у исходной. Связь клона не является признаком отмены.
6. Определить компонент по триггерам. Неоднозначно — записать **оба** варианта с цитатой-обоснованием и `confidence: low`. Выбирать молча запрещено.
7. Сгенерировать 3–10 сценариев на story. Структуры `Компонент:`/`Стенды:`/`Приоритет:` в описаниях **не существует** — acceptance criteria извлекаются из связного текста.

Предусловия и шаги писать **в терминах параметров шага**: не «в Ignite загружена карта», а «в IGNITE Cache `card-to-user-cache` ключ `2200123456789012` со значением `user_id=abc`». Имя кэша, ключ, имя топика становятся параметрами Gherkin-шага; без них генератор не соберёт исполнимый шаг. Формулировки «заполнен корректно», «аналогично предыдущему», «см. выше» запрещены — каждый сценарий самодостаточен.
8. Проставить `stand: "@st"` с пометкой, что это **дефолт**, а не вывод: в Jira поля стенда нет.
9. Присвоить `id` вида `gen-<release>-NN`, нумерация сквозная по файлу.
10. Записать YAML по схеме `docs/MANUAL_TEST_CONVENTIONS.md` плюс поля `id`, `story`, `story_tms_cases`, `component`, `stand`. Отброшенное — блоком `skipped`.
