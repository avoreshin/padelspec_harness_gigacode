Построй тест-модель релиза: {{args}} (ключ релиза `ASFMSTD-NNNN` типа `Release 2.0` либо ссылка; флаг `--force` — перезаписать существующий файл, сохранив уже выданные `id`).

**Тип задачи:** утилита тестировщика, **R1** — пишет только локальные файлы под git. Вне PDLC-loop'а, phase-gate transition не выполняется.

Выполни skill `tc-from-release`. Полная спецификация — в `${extensionPath}/skills/tc-from-release/SKILL.md`.

```
<PROFILE>   ${extensionPath}/scripts/testproject-profile.py   профиль тестового проекта
<COVERAGE>  ${extensionPath}/scripts/sdd-testcoverage.py      покрытие AC-* из SDD
```

## Acceptance criteria из SDD, если они есть

Есть `docs/sdd/` и в нём SDD, чья строка `**Story**` содержит ключ story, — сценарии строятся по его `AC-*`, и каждому кейсу проставляется `ac: AC-N`. Это делает связь «критерий → кейс» проверяемой: `python3 <COVERAGE> <release> --project .`.

Нет SDD — команда работает **ровно как раньше**: критерии извлекаются из описания story, поле `ac:` не проставляется, никаких отказов. Требование «у каждой story должен быть approved-SDD» живёт только в полном цикле `/pdls:test-workflow` и enforce-ится гейтом `sdd-coverage-gate`, а не этой командой.

## Куда попадает результат

В файл `docs/testcases/<release>.yaml`, и больше никуда. В TMS/Zephyr не выгружается, ключей `ASFMSTD-T####` не выпускается — идентификатор локальный, вида `gen-ASFMSTD-8441-01`, и он же становится Cucumber-тегом.

```
Jira: релиз + его связи → docs/testcases/<release>.yaml → человек правит → /pdls:generate-autotests
```

## Preflight — обязателен

| Проверка | Как |
|---|---|
| Профиль тестового проекта есть и актуален | `python3 <PROFILE> check` |
| Jira MCP настроен и живой | живой вызов `get_issue(<release-key>)` |
| Это релиз | issue type в ответе — `Release 2.0` |
| Состав непуст | среди `issuelinks` есть хотя бы одна `Story` вне связей клонирования |
| Контекст проекта на месте | **по профилю**: `docs/steps/` и `docs/tags.md` требуются только при `inventory_kind: cucumber-annotations` |
| Файл ещё не создан | `docs/testcases/<release-key>.yaml` отсутствует, либо задан `--force` |

**Первый запуск в проекте начинается с профиля, а не с Jira.** Профиля нет — **спроси у пользователя, где находится тестовый проект**, и заведи профиль командой `/pdls:test-project init <путь>`. Угадывать по текущему каталогу нельзя: тест-модель ведётся там, где заведён `docs/testcases/`, а автотесты могут лежать в соседнем репозитории — и написаны они не обязательно на Cucumber.

Прежнее требование «`docs/steps/` непуст и `docs/tags.md` существует» отвергало правильный проект на pytest, Robot Framework или без инвентаря шагов вообще. Тест-модель — это YAML со сценариями, она про фреймворк ничего не знает; знать про него должен профиль.

Проверка не прошла — **останови работу**, перечисли всё недостающее сразу, не создавай ничего. Тексты отказов — в skill'е.

Проверки TMS здесь нет намеренно: команда туда не пишет. Проверки `docs/harness/modules/` тоже нет — в проекте этот каталог существует, но **пуст**, и прежнее требование «непуст» отвергало бы правильный проект.

## Процесс

0. Профиль тестового проекта: `check` → нет профиля, спросить путь и `init`; разошёлся с проектом — сказать и предложить `/pdls:test-project refresh`.
1. Preflight.
2. Взять состав из **связей самого релиза**: `get_issue(<release>)` → `issuelinks` (либо `get_issue_links(<release>)`, если связи отдаются отдельно). Комментарии релиза не читаются: состав держится на связях, а не на тексте о них.
3. Отобрать участников состава.

| Связь | Действие |
|---|---|
| связанная issue типа `Story` | взять в работу |
| связанная issue типа `Bug` | отбросить — нет acceptance criteria |
| `clones` / `is cloned by` | исключить — связь о происхождении issue, а не о принадлежности этому составу |
| прочие типы связей | не фильтровать: типа «Состав релиза» (`id=11400`) в инсталляции нет |
| один ключ по нескольким связям | схлопнуть в один |

4. Ни одной Story среди связей — **стоп**: пустой состав это неразобранный вход, а не пустая тест-модель. В отказе перечислить все связи с типом и причиной отсева.

5. По каждой Story — `get_issue()` (за описанием и `resolution`, которого в связях нет), отбросить отменённые: `status.name` на `Отмен`/`Отклон` либо `Cancelled`/`Canceled`/`Rejected`; либо `resolution.name` ∈ `Отменено`, `Отклонено`, `Дубликат`, `Cancelled`, `Rejected`, `Duplicate`, `Won't Do`, `Won't Fix`. Связь живёт дольше задачи: story отменяют, а связь с релизом остаётся, поэтому вызов на каждую story обязателен.
5a. **По связи `clones` не ходить.** Релизы и story заводятся клонированием; описание клона бывает короче исходного. Читается только сама story, а состав — только собственные связи этого релиза. Описание пустое — story уходит в `skipped` с причиной, а не дочитывается у исходной. Связь клона не признак отмены — она признак происхождения, и в состав такая связь не берётся.
6. Определить компонент по триггерам. Неоднозначно — записать **оба** варианта с цитатой-обоснованием и `confidence: low`. Выбирать молча запрещено.
7. Сгенерировать 3–10 сценариев на story. Структуры `Компонент:`/`Стенды:`/`Приоритет:` в описаниях **не существует** — acceptance criteria извлекаются из связного текста.

Предусловия и шаги писать **в терминах параметров шага**: не «в Ignite загружена карта», а «в IGNITE Cache `card-to-user-cache` ключ `2200123456789012` со значением `user_id=abc`». Имя кэша, ключ, имя топика становятся параметрами Gherkin-шага; без них генератор не соберёт исполнимый шаг. Формулировки «заполнен корректно», «аналогично предыдущему», «см. выше» запрещены — каждый сценарий самодостаточен.
8. Проставить `stand: "@st"` с пометкой, что это **дефолт**, а не вывод: в Jira поля стенда нет.
9. Присвоить `id` вида `gen-<release>-NN`, нумерация сквозная по файлу.
10. Записать YAML по схеме `docs/MANUAL_TEST_CONVENTIONS.md` плюс поля `id`, `story`, `component`, `stand`. Отброшенное — блоком `skipped`.
