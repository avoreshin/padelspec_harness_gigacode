## [v0.8.5] - 2026-08-23

Релизный слой над сборкой расширения. Сборка публиковала контент автоматически и делала это исправно, но тег и релиз не создавала — их ставили руками, и в какой-то момент перестали: releases расширения показывали v0.8.1, когда в коде уже была v0.8.4. Теперь релиз выпускается тем же прогоном, что и сборка.

### Added

- **Релиз в обоих репозиториях выпускается автоматически.** После публикации расширения workflow создаёт релиз `vX.Y.Z` в `pdlc-harness` и в `padelspec_harness_gigacode`, если такого ещё нет. Идемпотентность проверяется по факту существования релиза, а не по diff'у push'а: шаг ведёт себя одинаково при повторном запуске, при `workflow_dispatch` и при нескольких push'ах с одной версией.

- **`scripts/release-notes.sh`** — печатает тело секции CHANGELOG для одной версии. Заметки релиза и changelog теперь один текст, разойтись им негде. Сравнение по точному номеру: без него `0.8.1` совпал бы с `0.8.10` — проверено на реальных секциях (4 строки против 7).

- **Гейт перед публикацией.** Публикация — force-push в репозиторий без истории, откатывать битую сборку не к чему, поэтому артефакт проверяется до push: `gigacode-extension.json` и `hooks/hooks.json` разбираются как JSON, `VERSION` в сборке совпадает с запрошенной версией, `verify-gigacode-hooks.sh` проходит по всем хукам (77 проверок). Каждое из трёх условий проверено отрицательным контролем — битый манифест, несовпадение версии и хук с синтаксической ошибкой останавливают публикацию.

### Fixed

- **`CHANGELOG.md` добавлен в `paths:` триггера.** Сборка вклеивает корневой changelog в CHANGELOG расширения, но в фильтре его не было: коммит, правящий только changelog, расширение не пересобирал, и там оставалась прошлая версия. До сих пор не проявлялось лишь потому, что каждый релиз одновременно менял и `.gigacode/**`.

### Changed

- **`build/gigacode/release-notes-footer.md`** — блок установки и обновления, который дописывается к заметкам релиза расширения. Этого нет в changelog и не должно быть: установка только по локальному пути, обновление через `reset --hard` вместо `pull` (репозиторий пере-выкладывается force-push'ем) и обязательный `/pdls:init-project` после установки нужны тому, кто ставит расширение, а не тому, кто читает историю изменений.


## [v0.8.4] - 2026-08-23

Ревизия трёх скиллов, работающих вне PDLC-loop'а: `find-dev-metrics`, `tc-from-release`, `autotest-generator`. Требования цикла на них не распространяются — evidence bundle, phase-gate и SDD здесь ни при чём. Правились только расхождения внутри самих скиллов: между тем, что написано в описании, и тем, что предписывает алгоритм.

### Fixed

- **`find-dev-metrics` затирал `metrics.md` без единой проверки.** Скилл перезаписывает файл в корне репозитория и не имел ни preflight, ни `--force` — запуск в не-Java проекте молча положил бы пустой отчёт поверх документа, написанного руками. Соседний `tc-from-release` от ровно того же затирания защищается явным отказом «Ничего не создано и не изменено», то есть скиллы расходились между собой. Добавлен Шаг 0: проект собирается Maven/Gradle, Micrometer подключён, `metrics.md` либо отсутствует, либо начинается заголовком, который ставит сам скилл. Иначе — отказ с тремя вариантами действий.

- **Шаг 4 требовал рендерить из снапшота то, чего снапшот не мог нести.** Шаг 5 печатает по каждой метрике «Описание», «Перцентили», «JMX», «Prometheus», «Условия инициализации» — ни одного из этих полей в `dev-metrics-scan.schema.json` не было, только свободное `notes`. Валидация снапшота проходила одинаково и когда рендерить есть из чего, и когда нечего, то есть шаг 4 ничего не подтверждал. Схема получила `description`, `percentiles`, `jmx`, `prometheus`, `init_condition`, `dynamic_name_example`, `section`; `percentiles` ограничены диапазоном `[0,1]` — проверено отрицательным контролем. `jmx`/`prometheus` допускают `null` и рендерятся как `❓`: «по коду не видно» и «нет» — разные ответы.

- **`find-dev-metrics` заявлен универсальным, зашит под один проект.** Frontmatter обещает «сканирует Java/Spring Boot проект», внутри — девять секций отчёта конкретной кодовой базы с прямым запретом «не создавай новые, не удаляй существующие», список обёрточных методов чужого хелпера (`incrementRequestsByDomain`, `updateIntGauge`) и примеры с `MetricsHolder.initMetrics()`. На любом другом сервисе это давало отчёт с чужими заголовками, часть из которых пуста. Секции теперь выводятся из самих метрик проекта (префикс имени + пакет регистрации), прежний список остался как образец формулировок. Обёрточные методы ищутся не по именам, а через классы, держащие `MeterRegistry`: прежний поиск по `.register(` и `increment(` матчил `ObjectMapper.registerModule` и любой доменный счётчик наравне с метриками.

- **`--force` в `tc-from-release` рвал связь с feature-файлами.** `id` — join key: он стоит тегом `@gen-*` в сценариях и записан обратно в YAML полем `feature:`. Перегенерация выдавала нумерацию заново, то есть рвала обе связи разом; скилл предупреждал об этом, но починки не предлагал. Теперь `--force` перечитывает файл до генерации и переносит уже выданные номера, сопоставляя по `story` + `name`; новые номера получают только новые сценарии, а номер исчезнувшего не переиспользуется — он занят тегом в `.feature`.

### Changed

- **`.dev-metrics-scan.json` добавлен в `.gitignore` целевого проекта.** Скилл писал «целевой проект должен добавить его в свой `.gitignore`», но `init-project.sh` добавлял шесть правил, и этого среди них не было — транзиентный снапшот всплывал в `git status` после каждого запуска `/find-metrics`.

- **Комментарий в `build-gigacode-extension.sh` противоречил инсталлятору.** Он утверждал, что каталога `.gigacode/` в проекте пользователя «нет», — при том что `scripts/init-project.sh` раскладывает именно его, а README расширения описывает `/pdls:init-project` как обязательный шаг после установки. Два корня здесь осознанны: команды опираются на `${extensionPath}`, потому что обязаны работать сразу после установки; скиллы и хуки — на `.gigacode/`, потому что им нужно состояние проекта (`.cost/`, audit trail), которого в каталоге расширения нет. Комментарий приведён к этому.

- **Описание блокировки тестов в `autotest-generator` приведено к текущему хуку.** Скилл цитировал `{"decision":"block"}` в stderr — формат, который `test-files-protector.sh` перестал печатать в v0.8.3 (теперь `{"decision":"deny", …}` в stdout). Поведение скилла было верным, устарела цитата.


## [v0.8.3] - 2026-08-23

Ревизия enforcement-слоя по фактам обоих рантаймов. Хуки писались под контракт, которого нет ни в GigaCode, ни в GigaCode / GigaCode, поэтому часть политики не применялась, а smoke-suite этого не показывал: фикстуры повторяли ту же выдумку, что и код. Проверено запуском, а не чтением.

Справочники, по которым сверялись поля:
[GigaCode](https://code.gigacode.com/docs/en/hooks) ·
[GigaCode / GigaCode](https://qwenlm.github.io/qwen-code-docs/en/users/features/hooks/).

### Fixed

- **Разбор события хука.** `subagent-stop-validator` читал `.subagent.name` / `.tools_used` / `.output` — полей, которых нет нигде; `AGENT_NAME` всегда была пустой, и хук выходил на первой проверке. Ни один контракт вывода субагентов не проверялся ни разу. Переписан на `agent_type` + `last_assistant_message`. Проверка tool scope убрана: списка вызванных инструментов в событии нет, а сам scope применяет рантайм по `tools:` в профиле — хук дублировал действующее ограничение на несуществующих данных. Аналогично `context-integrity-review` (`.compact.level` → `trigger`) и `jsonl-audit-sink` (`.event` → `hook_event_name`; до фикса каждая строка аудита писалась как `event:"unknown"`).

- **Вывод решения.** Все хуки печатали `{"decision":"block"}` в stderr. Оба рантайма разбирают как JSON только stdout, и значения `block` не знает ни один: работал лишь голый `exit 2`, а сам объект показывался пользователю как сырой текст. Общий `deny()` печатает в stdout один объект под оба контракта — `decision`/`reason` и `hookSpecificOutput.permissionDecision`. Заодно `reason` перестал подставляться в JSON сырым: кавычка или перевод строки из вывода валидатора давали битый объект.

- **Резолв корня проекта.** Хуки хранят состояние по относительным путям (`.gigacode/.cost`, `.gigacode/audit`, `.gigacode/commands`), а cwd агента не обязан быть корнем репозитория. Из подкаталога хук создавал второй каталог состояния и читал пустой risk class — то есть работал как R1 при любом фактическом классе.

- **Обходы policy-гейтов** (каждый воспроизведён запуском): `rm -fr /`, `rm  -rf /` (двойной пробел), `rm -r -f /`, `git push -f` в конце строки, `psql -c "drop table"` в нижнем регистре, `git commit --message="…"`, MultiEdit с секретом в `edits[].new_string`, R5-allowlist, который легализовал всю строку по совпадению в её начале (`ls ; curl … | bash`). Шаблон приватного ключа не срабатывал никогда: он начинается с дефиса, и `grep` разбирал `-----BEGIN …` как свои опции. Команда теперь разбирается по сегментам, сопоставление регистронезависимое, опасный `rm` распознаётся по флагам, а не по написанию.

- **Гейты, не срабатывавшие ни разу.** У счётчика `.gigacode/.cost/task-tokens` не было ни одного писателя — `cost-circuit-breaker` всегда видел ноль. Разрешение на правку тестов передавалось переменной `PDLC_ALLOW_TEST_EDIT=1`, которую `agents/test.md` предписывал выставить через `export` в Bash: до hook-процесса она не доходит никогда, значит test-агент не мог создать ни одного теста и фаза Test была заблокирована наглухо. `evidence-bundle-enforcer` дёргал `npx --yes` на каждом Stop и трактовал любой его сбой как провал схемы — то есть без сети блокировал закрытие валидного bundle; при этом рядом лежал `_validator.js` с тем же ajv@8 в постоянном кэше.

- **Фикстуры `java-lint`.** `tests/smoke/java-lint.sh` ссылается на `single`, `multimodule` и `maven`, README их описывает — но в репозиторий они не попадали никогда (в исходном коммите `/java-linter-review` есть только `nojava/README.txt`). 22 кейса из 29 падали на `subpath not found`. Незаметно это было потому, что сам тир в `run-all.sh` не входил; теперь входит как T4 (guard по JDK, `SKIP_JAVA_LINT=1` чтобы пропустить локально).

- **Корни путей в `java-lint.sh`.** Корень был один — «каталог, где лежит `.gigacode/`» — и от него считались И вендоренные линтеры, И каталог отчётов. При drop-in установке они совпадают, поэтому расхождение не замечалось; в GigaCode-расширении скрипт живёт в `${extensionPath}/scripts/`, и отчёты уезжали в родительский каталог установленного расширения вместо анализируемого проекта. Разделено: `HARNESS_ROOT` (ресурсы, рядом со скриптом) и `PROJECT_ROOT` (рабочая директория, туда же отчёты); оба переопределяются переменными окружения.

- **Зависание хука на пустом stdin.** Payload читается явным `hook_read_payload`. Чтение при подключении `lib/common.sh` по условию `[[ ! -t 0 ]]` выглядит удобнее, но вешает намертво любой хук, вызванный без данных с унаследованным открытым дескриптором — фоновый запуск, CI, вложенный прогон тестов: `cat` ждёт EOF, которого не будет.

- **`checksums.sha256`** для вендоренных линтеров: файл числился в README как integrity-gate, но его не было, и `java-lint.sh` каждый раз писал `integrity: skipped reason=no_checksums_or_shasum`. Подлинность `checkstyle-10.21.0-all.jar` сверена с `versions.lock` напрямую и совпала.

### Added

- **`hooks/token-usage-meter.sh`** (Stop + SubagentStop) — писатель счётчика токенов: берёт расход из полей события (`input_tokens` / `context_usage`), иначе суммирует `usage` по строкам `transcript_path`. Счётчик монотонный, обнуляется в `set-risk-class.sh` на старте задачи.
- **`scripts/test-edit-window.sh`** (`open` / `close` / `status`) — окно правки тестовых файлов через файл-маркер, видимый и агенту, и хуку. Кто и зачем открыл, пишется в лог.
- **`stop_hook_active`** учитывается в `evidence-bundle-enforcer` и `subagent-stop-validator` — без него отказ на Stop уводил сессию в цикл «остановился → заблокировали → остановился».
- **Suites 13–16** в `tests/smoke/hooks-extended.sh`: контракт вывода решения, закрытые обходы, ранее неработавшие гейты, устойчивость к пустому stdin. **Tier D** в `tests/smoke/java-lint.sh`: ресурсы берутся из обвязки, отчёты пишутся в анализируемый проект. Каждый кейс краснеет при возврате прежнего поведения — проверено. T2: 38 → 80 кейсов; всего 161 (33 + 80 + 16 + 32).

### Changed

- README приведён к коду: описания шести хуков (`prompt-validator` — не «запрет prompt injection», а advisory-напоминание про SDD; `context-integrity-review` — snapshot, а не supply chain; `subagent-stop-validator` — контракт вывода, а не запрет эскалации прав; `cost-circuit-breaker` — бюджет на задачу, а не дневной лимит; `ai-code-quality-gate` — линт после записи, без typecheck), число хуков и кейсов, отдельный статус `java-lint.sh` (в `run-all` не входит).
- В шапках `destructive-command-blocker` и `pii-boundary-check` и в README зафиксирована граница применимости: сопоставление шаблонов с текстом команды принципиально обходится, это defense-in-depth поверх `permissions.deny`, а не граница безопасности; пять regex — не замена gitleaks/trufflehog.
- Ссылки на SDD и roadmap в комментариях помечены как живущие в рабочем репозитории `pdlc-harness-work` — рядом этих файлов нет и не должно быть.
- `.gitignore`: добавлен `.gigacode/.cost/` — runtime-состояние не должно попадать в коммиты.

## [v0.8.2] - 2026-08-21

Две команды тестировщика для проекта `orchestrator-autotest`: от состава релиза в Jira до Cucumber-сценариев, дописанных в существующие feature-файлы. Специфика проекта зашита в skills осознанно — так же, как `/find-metrics` привязан к Java/Spring/Micrometer.

Спецификация построена на четырёх раундах проверки фактов в реальном проекте. Это оказалось не формальностью: из первоначальных предположений не подтвердилась половина, включая несущие. Ниже помечено, что именно.

### Added

- **`/generate-test-cases <release> [--force]`** + skill `tc-from-release` — строит тест-модель релиза `ASFMSTD-*` в `docs/testcases/<release>.yaml`. [`feat(commands): add /generate-test-cases and /generate-autotests (v0.8.1)`]

  **Состав релиза читается из таблицы в комментарии бота, а не из связей issue.** Предполагавшийся link type «Состав релиза» `id=11400` в инсталляции **не существует**; `fixVersion` для привязки не используется, description релиза пуст. Состав публикует бот `JIRA_TECHUSER_S` Markdown-таблицей в комментарии к issue типа `Release 2.0`.

  Берётся последний по времени комментарий с таблицей. Их бывает несколько, и состав в них разный: в наблюдённом релизе ранние таблицы содержат три story, которые позже отменили, а последняя — три пришедшие им на замену. Сортировка по дате создания, а не по названию стадии: комментарий «ФОРМИРОВАНИЕ → ГОТОВ К СТАБИЛИЗАЦИИ» встречался опубликованным позже, чем «СТАБИЛИЗАЦИЯ → ГОТОВ К ПСИ».

  Разбор опирается на заголовки колонок, а не на позиции, потому что формат задаёт бот. Формат не узнан — команда останавливается и печатает сырой текст комментария вместо того, чтобы угадывать.

  **Отменённые задачи в работу не берутся.** Взятие последней таблицы отсекает отменённое в типовом случае, но статуса в таблице нет, а story могут отменить и после публикации — поэтому по каждой строке делается `get_issue()`. Фильтр смотрит оба поля: `status.name` (`Отмен*`, `Отклон*`, `Cancelled`, `Canceled`, `Rejected`) и `resolution.name` (`Отменено`, `Отклонено`, `Дубликат`, `Cancelled`, `Rejected`, `Duplicate`, `Won't Do`, `Won't Fix`) — в части workflow задачу закрывают штатным статусом, а признак отмены живёт только в резолюции. Deny-list, а не allow-list: список рабочих статусов не фиксирован, и allow-list молча терял бы живую задачу с незнакомым статусом. `statusCategory` не годится — Jira относит отменённые к той же категории `Done`, что и завершённые.

  **Три вещи скилл знать не может, и говорит об этом прямо.** Есть ли уже автотест по story — определить нельзя: сценарии тегируются ключами TMS, а связь «TMS-кейс → story» живёт в TMS, куда доступа нет. Стенд не выводится ниоткуда — в Jira такого поля нет, тег ставит тестировщик, поэтому проставляется `@st` с явной пометкой «дефолт». Компонент часто неоднозначен — записываются два варианта с цитатой-обоснованием, выбирает человек.

  Взамен дедупликации — счётчик уже заведённых ручных кейсов TMS по каждой story (читается из таблицы состава) и список похожих сценариев из целевого файла. Решение о дубле принимает человек, глядя на оба.

- **`/generate-autotests <release|id-list|path>`** + skill `autotest-generator` — генерирует Cucumber-сценарии из тест-модели и дописывает их в существующие feature-файлы. Работает полностью offline.

  **Инвентарь шагов строится до генерации, а не сверяется после.** Прежний порядок — сгенерировать по статической таблице, потом сверить с кодом — означал, что генерация опирается на снимок, который протухает молча. Теперь инвентарь собирается первым, и сценарии пишутся только из него.

  **Контракт — аннотации, документация только семантика.** Это не принцип, а вывод из фактов: `docs/steps/rules.md` документирует параметр `{id}`, которого среди девяти `ParameterTypes` нет вовсе, и пишет `"ruleName"` там, где в коде `{string}`; в `docs/tags.md` отсутствует `@smoke`, использованный в feature-файлах 56 раз, и три тега очистки. Матчинг идёт по `@Когда`/`@Тогда` и `ParameterTypes.java`; `docs/steps` даёт описание, привязку модуль→класс и колонку «Пример» — готовый образец строки с реальными значениями.

  **Ненайденный шаг не выдумывается.** Выводится блок с местом поиска, тем что не покрыто, ближайшим совпадением и разбором почему оно не подошло, и предлагаемой сигнатурой нового шага. Ближайшее совпадение обязательно: `{isRecord}` = «есть запись\|нет записи» уже покрывает проверку отсутствия, и без подсказки человек написал бы дубль поверх работающего step definition.

  Инвентарь заведомо неполон: glue-пакеты `ru.sbrf.fraud.at.{core,web,rest}.stepdefs` приходят транзитно из `fraud-utils` и не документированы, jar в `~/.m2` отсутствует. Поэтому формулировка — «не найден в локальном инвентаре, возможно приходит из glue-пакетов», а не «шага нет».

  **Дописывание в существующий файл — норма.** Подтверждено git log: новые feature-файлы под story в проекте не заводятся, один файл на компонент. Выбор файла объясняется по каждому сценарию — ошибка маршрутизации обнаружилась бы только на прогоне регресса.

  **Теги очистки.** Сценарий, создающий сущность и не несущий парного тега, оставляет мусор на общем стенде. Документированного соответствия «шаг создания → тег очистки» в проекте нет — тестировщик подбирает по смыслу, значит и скилл надёжно не выведет. Тег подбирается по таблице наблюдённых пар и помечается как **предложенный**; пара не нашлась — прямое предупреждение.

  Allure-метки копируются у соседнего сценария и помечаются в отчёте: выдумать `functionalArea` хуже, чем не проставить — неверная метка молча портит группировку отчёта.

- **Идентификатор `@gen-<release>-NN`** — например `@gen-ASFMSTD-8441-01`, плюс тег ключа story. Сегмент `gen-` читается как «сгенерировано, в TMS не заведено», не матчится regex-ом `@tmsLink=([A-Z]+-T?\d+)` и не путается с ключом TMS `ASFMSTD-T1174`, на который иначе был бы визуально похож. `@tmsLink=` не выставляется: записи в TMS нет, а фальшивая ссылка сломала бы существующий разбор.

- **Три проверки, заимствованные из скилла генерации ручных тест-кейсов соседней команды** — идеи чужие, механизм наш: контрактом остаются существующие файлы проекта, а не документация.

  **Инвентарь атрибутов.** Правило «не выдумывать» раньше действовало только на шаги. Шаг мог быть найден в инвентаре, а таблица под ним — содержать поле, которого в системе нет; расхождение всплыло бы на прогоне. Инвентарь имён параметров собирается по существующим feature-файлам и привязан **к шагу**, а не глобален: `отправить плоский JSON запрос ... с параметрами` принимает не то же, что `создать онлайн-факт ... с параметрами`. Формулировка предупреждения — «атрибут не встречался в существующих сценариях», а не «не существует»: инвентарь неполон так же, как инвентарь шагов.

  **Проверка stash-переменных.** Использование `#{X}` раньше, чем переменная положена, — гарантированно падающий тест, и это проверяется механически. Определением считаются **три** места: блок `Предыстория:` целевого файла, шаг выше в самом сценарии, и `docs/stashKeys.md` — там ключи, которые кладут хуки, поэтому `#{ID последнего события}` валиден без явного шага сохранения.

  `Предыстория` — обязательный источник, а не дополнительный: она выполняется перед каждым сценарием файла, и на практике именно там генерируются `id`, номер карты и временные отсечки. Проверка без неё выдала бы ложное предупреждение на каждую такую переменную, после чего человек перестал бы читать предупреждения вообще. Отсюда же второе правило: переменная уже есть в `Предыстория` — использовать её, свой шаг сохранения не добавлять, а расхождение выносить в отчёт.

  **Совместимость типов stash-значений.** Одного факта определения мало. Наблюдённое падение: `timestamp` сохранён строкой через шаг форматирования, а шаг вычисления времени ожидает `LocalDateTime` — `ClassCastException` на рантайме при формально корректном сценарии. Ведётся таблица наблюдённых пар «шаг-источник → тип» и «шаг-потребитель → требуемый тип»; комбинации нет в таблице — скилл молчит: таблица заведомо неполна, и ложное предупреждение тут хуже пропущенного.

  **Отчёт строится по перечитанным файлам, а не по намерению.** Сводка «✅ 2 файла, 9 сценариев» — утверждение о состоянии диска; собранное по памяти о собственном намерении, оно промолчит, если запись частично не прошла. Теперь после записи файлы перечитываются, из них собираются теги `@gen-*`, и расхождение выводится отдельной строкой, а не правит счётчик молча. `feature:` в YAML проставляется только блокам, чьи теги реально найдены.

- **Предусловия и шаги тест-модели пишутся в терминах параметров шага.** Не «в Ignite загружена карта», а «в IGNITE Cache `card-to-user-cache` ключ `2200123456789012` со значением `user_id=abc`». Причина отличается от той, по которой самодостаточности требуют от ручных кейсов: там она нужна тестировщику, чтобы не листать документ, здесь — генератору, чтобы собрать исполнимый шаг. Имя кэша, ключ, имя топика становятся параметрами Gherkin; расплывчатое предусловие не конвертируется и уходит в отчёт как ненайденный шаг. Формулировки «заполнен корректно», «аналогично предыдущему» запрещены.

- **`--tc=<id-list>` в `/test`** — опциональный вход: acceptance criteria берутся из тест-модели вместо AC из SDD. Без флага поведение не меняется.

### Fixed

- **CHANGELOG расширения был заглушкой-указателем, а не реальными записями.** `build-gigacode-extension.sh` генерировал `CHANGELOG.md` расширения через heredoc из трёх строк («версия v…, см. releases / source changelog»), поэтому в `padelspec_harness_gigacode` не было истории изменений. Теперь build кладёт короткий заголовок + **полный source-CHANGELOG** (`cat CHANGELOG.md`) → в расширении реальные секции всех версий. Проверено: сборка v0.8.1 содержит 27 версий-секций.
- **Preflight `/generate-test-cases` отвергал правильный проект.** Проверка требовала непустой `docs/harness/modules/`; в `orchestrator-autotest` этот каталог существует, но **пуст**. Контекст теперь берётся из `docs/steps/` и `docs/tags.md`, которые есть и наполнены.
- **Preflight `/generate-autotests` искал несуществующий каталог.** Требовалось наличие `core/` либо `debug/` внутри каталога feature-файлов; `core/` в проекте не существует, а `debug/` — отладочные тесты вне регресса, куда релизные сценарии писать нельзя. Путь зафиксирован как `src/test/resources/features/`, добавлен поиск runner с `@CucumberOptions` — без него неизвестен `glue`.

### Why

Тест-кейсы по составу релиза заводились вручную, а автотесты писались по ним отдельно, второй раз перечитывая те же story. Обе операции механические, но ошибка в них дорогая: автотесты живут в общей кодовой базе, а созданные тестом сущности — на общем стенде.

Разрыв между командами оставлен намеренно: человек смотрит тест-модель до того, как из неё поедет код.

### Известные ограничения

- Тест-модель существует только в git — TMS её не хранит, поэтому `docs/testcases/<release>.yaml` обязан коммититься. Выгрузка в Zephyr запланирована **третьим шагом конвейера** через XML-импорт, а не через MCP: Zephyr Scale принимает массовую загрузку файлом, без API и токенов, и то же ограничение по MCP зафиксировала у себя соседняя команда. Схема YAML под это готова — она с самого начала следует `MANUAL_TEST_CONVENTIONS.md` и ложится на XML один к одному.
- Дедупликация против автотестов, написанных человеком, невозможна: связи story↔сценарий в репозитории нет. Смягчение — два списка для глаз, не автоматическая проверка.
- Стенд всегда `@st` по умолчанию: в Jira поля стенда не существует.
- Инвентарь шагов неполон на величину glue-пакетов `fraud-utils` — их исходники недоступны, Maven не поднимается из-за корпоративного Nexus.
- Флаг `--verify` (dry-run Cucumber) реализован, но **не проверен**: в среде сбора фактов Maven не запустился, поведение на неизвестном шаге не подтверждено.
- Разбор таблицы состава зависит от формата, который задаёт бот Jira. При изменении формата команда остановится с печатью сырого текста — но остановится.
- Генерация LLM-зависима и smoke-уровнем не покрывается — см. `tests/README.md`, раздел «Что НЕ покрыто».

- **Неполная установка обвязки тоже вела к fail-open.** Если каталога `hooks/lib/` нет (хук скопирован без него — так делал и `setup_temp_repo` в `tests/smoke/hooks-core.sh`), `source` падал, и под `set -e` хук завершался с **exit 1** — снова «не сработал, продолжаем». Все подключения переведены на `source … || exit 2`.

- **`$(dirname "$0")` в подключении библиотек — внешняя зависимость там, где её быть не должно.** В урезанном окружении без `dirname` гейт молча не подгружался бы, то есть отказ ровно того вида, который он закрывает. Заменено на раскрытие bash `${BASH_SOURCE[0]%/*}` — без внешних команд.

- **`harness.sh doctor`:** `jq` переведён в `REQ_BINS` с install-подсказкой. Доктор обязан краснеть на машине, где enforcement применить нельзя.

- **`verify-gigacode-hooks.sh` рапортовал ложное «wiring не найден» для любой корректной сборки.** В манифесте v3 ключ `hooks` — это строка-путь (`"hooks/"`), а не wiring-словарь; `emit()` вызывал на ней `.items()` и падал с `AttributeError` на первом же источнике, не доходя до `hooks/hooks.json`, где лежат настоящие привязки. `2>/dev/null` прятал traceback, поэтому наружу шло «Без wiring GigaCode не знает, когда вызывать хуки — они не сработают никогда». Главная проверка доктора была сломана и пугала ложной тревогой. Добавлены проверки типов и изоляция источников друг от друга. На собранном расширении: было `FAIL — wiring не найден`, стало `PASS — найдено wired-привязок: 20`.

- **Сборка расширения падала на Windows** (`scripts/build-gigacode-extension.sh`) — тот же cp1251, что в v0.7.2, но в корневом `scripts/`, который тогда не попал в скоуп правки. В CI (Linux/UTF-8) не воспроизводится, поэтому не всплывало.

- **Расширение, собранное на Windows, уезжало с CRLF в хуках** — `bash` на таком файле падает с `$'\r': command not found`, то есть установка выглядела успешной, а хуки не работали. Две причины: `cp -R` копирует рабочую копию как есть (`core.autocrlf=true`), а Python в текстовом режиме на Windows пишет CRLF. Все записи в сборке переведены на явный `newline="\n"`, плюс финальная нормализация `.sh`. Публикуемые сборки не были затронуты (workflow идёт на `ubuntu-latest`), но локальная сборка молча давала битое расширение. Прогон хук-доктора по сборке: было `PASS 55 · FAIL 17`, стало `PASS 72 · FAIL 0`.

- **Текст блокировки `require-jq.sh` ссылался на путь `.gigacode/scripts/harness.sh`,** которого в GigaCode-установке нет (там `${extensionPath}/scripts/`). Переписан на команду — `/harness doctor`, в GigaCode `/pdls:harness doctor`.

### Fixed

- **`/harness hooks list` падал на Windows с не-UTF-8 локалью.** `hooks_list` печатает заголовок с эмодзи 🪝 (U+1FA9D) из python3-heredoc; при `sys.stdout.encoding = cp1251` это `UnicodeEncodeError` и exit 1 — команда не работала вообще. Все три python3-вызова в `harness.sh` переведены на обёртку `py()` (UTF-8 Mode, PEP 540), чтение и запись `settings.json` получили явный `encoding='utf-8'`.

Тот же класс дефекта, что фикс 4a в v0.7.1, и то же последствие — Stop-хук не даёт закрыть сессию. Проверено: 5 из 7 схем репозитория не декодируются в cp1251.
- **`verify-gigacode-hooks.sh` мог тихо отрапортовать ложное «wiring не найден».** `parse_wiring` печатает пути установленного расширения; если в пути есть не-ASCII (напр. `C:\Users\Иван\…`), печать падала, а `2>/dev/null` прятал traceback — вывод выглядел пустым, и доктор сообщал, что привязки хуков не найдены. Добавлен UTF-8 Mode (явный `encoding` на чтении там уже был).

### Added

- **S2.9–S2.11** в `tests/smoke/scripts.sh` — регрессия на локаль-независимость. Кейсы воспроизводят проблему **портируемо**, поэтому ловят регрессию и в Linux-CI, а не только на машине с русской локалью: `PYTHONIOENCODING=cp1251` эмулирует не-UTF-8 вывод, `PYTHONWARNDEFAULTENCODING=1` + `PYTHONWARNINGS=error::EncodingWarning` (PEP 597) превращает любой `open()` без `encoding=` в ошибку. ## [v0.7.1] - 2026-08-11

### Added

- **`implement-iteration-cap-gate.sh`** — 16-й enforcement-хук (PreToolUse · Bash). Делает iteration cap `/implement` детерминированным: блокирует вызов `emit-phase-event.sh`, записывающий 4-ю (и далее) попытку implement-фазы со `status=pass|iterate` вместо обязательного `escalate`. На каждый `pull_request`, трогающий `.gigacode/**` или `tests/**`, гоняет `tests/smoke/run-all.sh --verbose` и `.gigacode/scripts/validate-schemas.sh all` на `ubuntu-latest` (+ `workflow_dispatch` для ручного прогона). ### Fixed

- **`evidence-bundle-enforcer.sh` блокировал сессию на любом хосте с Node.** Стратегия 4a звала `npx --yes -p ajv-cli ajv validate -c ajv-formats …`, но `ajv-cli@5` не тянет `ajv-formats` в зависимостях (проверено по npm-реестру) — флаг `-c ajv-formats` требовал require'нуть отсутствующий модуль, npx возвращал ненулевой код, и хук трактовал это как «bundle не прошёл схему», хотя bundle валиден. Добавлен `-p ajv-formats` в вызов (ср. `.gigacode/scripts/_validator.js`, который ставит `ajv@8 + ajv-formats@3` явно). Баг был невидим, потому что: на хосте без Node ветка 4a пропускается и работает jq-smoke, а в smoke-suite его ловит единственный положительный кейс `S1.5` — остальные кейсы Suite 1 и так ожидают блокировку, поэтому системный сбой валидатора в них не проявляется. **Найден первым же прогоном нового `harness-ci`** (Node ставится в job → включается ветка 4a).
- **`dev-metrics-scan.schema.json` не компилировалась валидатором обвязки.** Схема (добавлена в v0.7.0) объявляла `$schema: draft-07`, тогда как `_validator.js` поднимает Ajv в режиме draft 2020-12 (`ajv/dist/2020.js`) и мета-схему draft-07 не знает → `validate-schemas.sh compile` падал на ней. Вдобавок объявление противоречило содержимому: схема использует `$defs` — ключевое слово 2019-09+, в draft-07 его нет (там `definitions`). Приведена к `https://json-schema.org/draft/2020-12/schema`, как остальные 6 схем репозитория. Тоже поймано `harness-ci` — шаг schema-валидации до этого ни разу не выполнялся.
- Счётчики покрытия в шапках `tests/smoke/run-all.sh` и `hooks-extended.sh` отстали ещё с v0.6.0 (заявляли «8 хуков / 13 кейсов», хотя Suite 9–10 для `commit-message-format`/`branch-naming-gate` уже были добавлены). Синхронизированы с фактическим состоянием, там же обновлены числа в README.

### Why

`/implement` документирует iteration cap («Iteration cap: 3. На 4-й попытке — mandatory escalation», GIGACODE.md §9), но ни один хук его не проверял: модель сама читала счётчик через `workflow-state.sh`, сама считала и сама решала остановиться — ровно тот сценарий, от которого предостерегает собственный README harness'а («Модель проигнорировать может — хук нет»). Аналогично требование «после любого изменения хуков или схемы прогнать `tests/smoke/run-all.sh`» существовало только текстом в README и ничем не проверялось.

### Известные ограничения

- **INV-1:** хук перехватывает **запись** 4-й попытки, а не саму 4-ю правку кода — обобщённый PreToolUse-хук не может надёжно связать произвольный Edit/Write с конкретной задачей и итерацией. То же принятое ограничение, что у `sdd-schema-gate.sh` (валидация в момент записи, не раньше).
- **INV-2:** `harness-ci` делает проверку видимой на PR, но **не блокирует merge** сам по себе — required status check включается вручную в branch protection rules и файлами репозитория не настраивается.

- **Гейт сборки для SpotBugs:** после каждого успешного прогона команда через `AskUserQuestion` спрашивает разрешение на `mvn clean package -DskipTests=true`; при согласии проект собирается (без тестов) и SpotBugs прогоняется по свежим классам (phase 2, флаг `--build-spotbugs`).
- **Флаги CI:** детерминированные счётчики находок (`total_findings`, per-linter `count:`), SHA-256 integrity-gate (`--no-verify` для обхода), `--fail-on <any|high|N>` (exit 5 для pipeline), `--keep`, `--min-tokens N` для CPD.
- **Smoke** `tests/smoke/java-lint.sh` (29 кейсов: Tier A discovery/ветки, Tier B контракт SARIF/XML-артефактов, Tier C счётчики/integrity/latest/fail-on) + fixtures `tests/fixtures/java-lint/{single,multimodule,maven,nojava}` с умышленными smells. Guard: SKIP при отсутствии JDK 17+ / линтеров (suite остаётся зелёным).

### Обязательные проверки (всегда присутствуют в отчёте)

- **Неиспользуемые переменные / методы / импорты (dead code)** — PMD (`UnusedPrivateField/Method`, `UnusedLocalVariable`, `UnusedFormalParameter`, `UnusedAssignment`, `UnnecessaryImport`) + Checkstyle (`UnusedImports`, `RedundantImport`, `UnusedLocalVariable`). Отдельная секция + действие REMOVE в рекомендациях.
- **Нарушения SOLID** — секция с оценкой по каждому принципу (SRP/OCP/LSP/ISP/DIP). SRP опирается на структурные сигналы PMD design-категории (`GodClass`, `TooManyMethods`, `TooManyFields`, `ExcessiveParameterList`, `CouplingBetweenObjects`, сложность) + ревью субагента. Пустой раздел не допускается.

### Why

Ревью Java-кода на структурные болячки (дублирование, god-класс, мёртвый код, нарушения SRP) — рутинная часть code-review, которую детерминированно закрывают индустриальные линтеры. Команда даёт это офлайн, воспроизводимо и с отчётом, сразу пригодным к работе (критичность + код + рекомендация).

### Design invariants

- **INV-1:** линтеры едут внутри harness — агент вызывает их прямо из папки, без сетевой докачки. JVM — единственное, что не вендорится.
- **INV-2:** verbose-вывод линтеров не попадает в основной контекст — только summary + путь (§8 token discipline).
- **INV-3:** отчёт создаётся на диске всегда, даже при отсутствии Java / JDK / линтеров (degraded baseline).
- **INV-4:** обязательные проверки (dead code + SOLID) присутствуют в каждом отчёте, даже с вердиктом «Не обнаружено».
- **INV-5:** supply-chain tripwire — сверка SHA-256 ключевых jar перед прогоном; несовпадение → `integrity: FAIL` + предупреждение в отчёте.

Initial release pdlc-harness. Базовая обвязка для GigaCode согласно AI DISRUPT PDLC v3.5.

### Added (от initial commit `575d3ea` до `1b13ef7`)

- **6 slash-commands** (`.gigacode/commands/`): `/sdd-new`, `/plan`, `/review`, `/evidence`, `/metrics`, `/risk-classify`.
- **`/init-project` command** — однокомандная установка harness'а в свежий repo с заполнением GIGACODE.md placeholders через AskUserQuestion. [`feat(init): one-command harness install via /init-project`]
- **6 subagent profiles** (`.gigacode/agents/`): `explore`, `plan`, `test`, `coding`, `review`, `security` — с per-role tool scope.
- **10+ enforcement hooks** (`.gigacode/hooks/`): `destructive-command-blocker`, `pii-boundary-check`, `evidence-bundle-enforcer`, `cost-circuit-breaker`, `prompt-validator`, `ai-code-quality-gate`, `context-integrity-review`, `subagent-stop-validator`, `slash-command-lint`, `jsonl-audit-sink`, plus новые: `test-files-protector`, `gigacode-md-placeholders`.
- **`test-files-protector.sh`** PreToolUse hook — блокирует Edit/Write для test files без `PDLC_ALLOW_TEST_EDIT=1`. [`feat(hooks): block edits to test files without explicit Test Agent opt-in`]
- **`gigacode-md-placeholders.sh`** SessionStart hook — warning, если в `.gigacode/GIGACODE.md` остались `<…>` placeholders. [`feat(hooks): SessionStart warns about unfilled GIGACODE.md placeholders`]
- `.gigacode/settings.json` — policy hooks framework (deny-first для destructive ops, secrets, evidence bundle enforcement).
- `.gigacode/schemas/evidence-bundle.schema.json` — single schema на этой версии.
- `.gigacode/templates/SDD-template.md`, `GIGACODE.md` template.
- `.gigacode/policies/risk-ladder.yaml` — R0..R5 maturity ladder.
- `.gigacode/scripts/` — `init-project.sh`, `collect-evidence.sh`, `test-hooks.sh`.

### Changed (от initial release)

- **Schema enforcement** evidence-bundle: validator теперь верифицирует **содержимое**, не только наличие файла. [`fix(hooks): evidence-enforcer now verifies content, not just schema`]

- **`evidence-bundle.schema.json`** — формализованы `git_context` и `test_hint`, enforce для R2+. [`feat(schema): formalize git_context and test_hint, enforce for R2+`]

## Release tooling

- **Release branches** — каждая `vX.Y.Z` фиксируется веткой `release/vX.Y.Z`, которая создаётся от main на момент release и больше не двигается (только hotfix patch'и).
- **Tags** — `vX.Y.Z` — immutable, ставятся на тот же commit, что HEAD release-ветки.
- **Conventional Commits** — `feat(scope): ...`, `fix(scope): ...`, `docs(scope): ...`, `refactor(scope): ...`, `chore(scope): ...`.
- Workflow подробно: [`docs/release-process.md`](docs/release-process.md).
